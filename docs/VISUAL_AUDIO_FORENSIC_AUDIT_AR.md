# التدقيق الجنائي للأصول المرئية والصوتية وحزم المحتوى — AshenKingdoms

**تاريخ اللقطة:** 2026-10-21  
**النطاق:** مراجعة ساكنة أولية للمستودع على الفرع `main`، تركز على الأصول المرئية والصوتية والسينمائية، إضافات Godot، أدوات توليد الأصول، سجل التراخيص، وحزم المحتوى.  
**المنصة الأولى:** Android؛ المطوّر: شخص واحد.  
**حالة الوثيقة:** تقرير فرز أولي وخطة تحقيق قابلة للتنفيذ، وليس شهادة بأن كل ملف ثنائي أو كل ترخيص أو كل مكوّن خارجي قد خضع لفحص جنائي كامل.

## 1. الخلاصة التنفيذية

المشروع لعبة RPG ثلاثية الأبعاد مبنية على Godot 4.6، وفيه بنية أولية لمسار الأصول وإضافتان داخل المحرر، وأداة اختيارية لتوليد نموذج لاعب عبر Meshy، وسجل مركزي للأصول. لكن وجود الأدوات لا يثبت وجود محتوى فني نهائي.

النتيجة المهمة من الملفات التي تمت مراجعتها:

- `assets/asset_manifest.json` يسجل أصلًا واحدًا فقط: أيقونة المشروع `assets/ashenkingdoms_icon.svg`.
- `docs/ASSET_CREDITS.md` يصرح بأن نموذج اللاعب الخارجي `assets/characters/player/player.glb` لم يُضف بعد، وأن مصدره ورخصته غير محددين.
- `docs/FREE_ASSET_PIPELINE_AR.md` يصف تنظيم الملفات وفحص الترخيص؛ الإضافة لا تولّد أصولًا ولا تنزّلها.
- `docs/PLUGIN_INTEGRATION_AR.md` يصف إضافة فحص GLB وأداة Meshy الاختيارية، لكن نجاح الفحص أو وجود السكربت لا يثبت وجود نموذج لاعب نهائي أو تحريك جاهز.
- `project.godot` يفعّل إضافتي `ashen_asset_bridge` و`ashen_free_asset_pipeline`، ويستخدم Godot 4.6 مع `gl_compatibility`، وهو قيد مهم عند اختيار خامات وإضاءة ومؤثرات موجهة إلى Android.
- لا تُعتبر هذه المراجعة إثباتًا على اكتمال خرائط عالية التفاصيل، أو أزياء ومعدات، أو مؤثرات صوتية، أو موسيقى، أو حوار صوتي، أو مشاهد سينمائية.

**الحكم الأولي:** الخطر الأعلى ليس نقص أداة توليد؛ بل احتمال الخلط بين بنية خط الإنتاج وبين وجود أصول نهائية موثقة ومختبرة. يجب أن يصبح لكل أصل أثر قابل للتتبع من المصدر إلى الملف المستورد، ثم إلى مشهد Godot واختبار Android.

### ما لا تثبته هذه اللقطة

لم تتضمن هذه الجولة فك كل ملفات المشروع الثنائية، أو حساب hashes لكل أصل، أو مراجعة كل ملف رخصة خارجي، أو تشغيل Godot محليًا، أو فتح الأصول في Blender، أو اختبار الأداء على هاتف حقيقي. لذلك لا نعلن «تدقيقًا جنائيًا كاملًا» مكتملًا. تُسجّل النتائج التالية كـ **نتائج أولية مبنية على الملفات التي تمت معاينتها**، وتُستكمل بالأوامر والبوابات الواردة أدناه.

## 4. بروتوكول جمع الأدلة

شغّل من نسخة عمل نظيفة، واحتفظ بناتج الأوامر في تقرير مؤرخ. لا تستبدل الأصول الأصلية أثناء التحقيق.

### 4.1 خط الأساس والأدوات

```bash
git status --short
git rev-parse HEAD
git branch --show-current
python3 --version
godot --version
```

إذا لم تتوفر Godot CLI محليًا، سجّل ذلك كاختبار غير منفذ بدل استنتاج النجاح.

### 4.2 جرد الملفات والامتدادات والأحجام

```bash
python3 - <<'PY'
from pathlib import Path
from collections import Counter
root = Path("assets")
files = sorted(p for p in root.rglob("*") if p.is_file())
print("asset_files", len(files))
print("extensions", dict(Counter(p.suffix.lower() or "<no-extension>" for p in files)))
for p in files:
    print(f"{p.stat().st_size}\t{p.as_posix()}")
PY
```

### 4.3 بصمات الملفات لاكتشاف التكرار أو التغير

```bash
python3 - <<'PY'
from pathlib import Path
from hashlib import sha256
from collections import defaultdict
root = Path("assets")
groups = defaultdict(list)
for p in root.rglob("*"):
    if p.is_file():
        h = sha256(p.read_bytes()).hexdigest()
        groups[h].append(p.as_posix())
for h, paths in sorted(groups.items()):
    if len(paths) > 1:
        print("DUPLICATE", h, *paths, sep="\n  ")
PY
```

لا تحذف النسخ المتكررة آليًا؛ فقد تكون نسخًا مقصودة أو ملفات مصدر وتصدير.

### 4.4 فحوص المشروع والتراخيص

```bash
python3 tools/validate_docs.py
python3 tools/validate_free_assets.py
godot --headless --path . --editor --quit
```

بعدها شغّل اختبارات المشروع المعتمدة في `docs/TEST_PLAN.md` وسجّل كل أمر ونتيجته. لا تُعتبر أي خطوة ناجحة إلا إذا نُفذت على رأس الفرع المسجل.

### 4.5 فحص المراجع المكسورة

- ابحث عن موارد Godot التي تشير إلى ملفات غير موجودة، ومشاهد لا يمكن تحميلها، وملفات import/cache لا تتوافق مع المصدر.
- افتح كل مشهد يستخدم نموذجًا أو خامة أو صوتًا، وسجّل مسار المورد ونتيجة التحميل.
- لا تعتمد على بحث نصي وحده للكشف عن كل المراجع؛ موارد Godot قد تحتوي معرفات أو مراجع مستوردة.
- راجع `.godot/imported` كمخرجات مولّدة لا كمصدر أصلي، ولا ترفع cache بدل الملفات المصدرية.

## 5. فحص كل أصل مرئي

لكل ملف GLB/glTF/OBJ/DAE أو صورة أو خامة أو فيديو، أنشئ سجلًا يتضمن:

1. معرفًا ثابتًا واسمًا واضحًا ومسار الملف.
2. SHA-256 وحجم الملف وتاريخ الاستيراد.
3. المصدر الأصلي ورابطه، والمؤلف، والرخصة ورابط نصها، والإسناد المطلوب.
4. السماح بالتعديل، والاستخدام التجاري، وإعادة التوزيع، والاستخدام في الألعاب، وقيود الذكاء الاصطناعي إن كانت مذكورة.
5. عدد المضلعات/المثلثات، وعدد المواد والخامات، وأبعاد الخامات، وعدد العظام ومقاطع التحريك عند انطباق ذلك.
6. مقياس النموذج ومحوره واتجاهه ومركزه، ومراجع الملفات الخارجية، وحالة UV/normal maps.
7. حالة التصادم وLOD، وحجم الذاكرة التقريبي، والنتيجة على Android.
8. المشاهد والأنظمة التي تستخدم الأصل، ونتيجة الاختبار، وقرار القبول أو الرفض، واسم المراجع وتاريخ القرار.

### شروط رفض فورية

- مصدر مجهول أو ترخيص غير قابل للتحقق.
- منع أو غموض في الاستخدام التجاري أو إعادة التوزيع للغرض المستهدف.
- ملف لا يفتح أو يحتوي مراجع خامات مفقودة.
- نموذج معطوب تشريحيًا أو هيكل عظمي غير صالح للأنيميشن المطلوب.
- محتوى مأخوذ من لعبة أخرى أو علامة تجارية أو شخصية محمية بلا تصريح مناسب.
- أصول مولدة لا تسمح شروط المزود بتوزيعها أو تعديلها كما تتطلب اللعبة.

## 6. بروتوكول الشخصيات والملابس والدروع والأسلحة

### الشخصيات

- اللاعب، الشخصيات غير القابلة للعب، الأعداء، الزعماء، المخلوقات، الشخصيات الخلفية.
- تحقق من silhouette، والنسب، والوجه واليدين، وتوافق المقياس، واتجاه `-Z` إن كان مطلوبًا من منطق المشروع.
- افصل نموذج العرض عن جسم التصادم ومكونات اللعب.
- اختبر idle/walk/run/jump/attack/hit/death، وتأكد من عدم وجود قفزات في الجذر أو اختراق واضح للملابس.

### الملابس والدروع

- سجّل القطعة ومقاسها ومادة سطحها ونقاط تثبيتها والعظام التي تتبعها.
- اختبر التقاطع مع الجسم خلال الحركة، ووزن الجلد، والشفافية، ووجوه السطح، وأولوية العرض.
- اعتمد نظام مجموعات متناسقة بدل قطع غير مترابطة بصريًا: مسافر، حارس الرماد، حداد، كاهن/راوٍ، عدو عادي، قائد، زعيم.
- لا تنشئ عشرات القطع قبل اعتماد نموذج واحد مكتمل من حيث الشكل والهيكل والأداء.

### الأسلحة

- سيف، فأس، خنجر، رمح، درع، أسلحة ثقيلة، وأسلحة زعماء بحسب حلقة اللعب الفعلية.
- افصل نموذج العرض عن منطقة الإصابة، وتحقق من موضع القبضة والمحور واتجاه الضربة.
- لا تجعل الاصطدام يعتمد على شكل الشبكة المرئية وحده؛ اختبر hitbox/hurtbox مع منطق القتال.
- أضف آثار الاستخدام والخدوش والخامات باعتدال، مع خامات مشتركة ومواد قليلة ملائمة للهاتف.

### البيئات والخرائط

- جرد مشاهد العالم، والتضاريس، والمباني، والطرق، والكهوف، والبوابات، والديكورات، والنباتات، والسماء، والضباب، والإنارة.
- تحقق من scale consistency، وطرق الملاحة، وحدود العالم، والتصادم، والاختفاء خارج الكاميرا، والموارد المتكررة.
- اختبر مناطق اللعب مع مسار واضح للّاعب ونقاط اهتمام وتباين بصري قابل للقراءة، وليس مجرد كثافة تفاصيل.
- راقب overdraw والشفافية والظلال وdraw calls وذاكرة الخامات على Android.

## 7. التدقيق الصوتي

لكل ملف صوتي سجّل: المصدر، الرخصة، SHA-256، المدة، معدل العينة، عدد القنوات، peak/RMS أو LUFS عند توفر أداة قياس، وحجم الملف، وموضع الاستخدام داخل اللعبة.

### مجموعات الصوت المطلوبة

- البيئة: رياح، رماد، مطر، نار، غابة، كهف، معدن، قرية، داخل المباني.
- الحركة: خطوات بحسب السطح، ركض، قفز، هبوط، احتكاك الدروع والملابس.
- القتال: سحب السلاح، swing، impact، block/parry، إصابة اللاعب، موت العدو، المؤثرات السحرية.
- الواجهة: فتح/إغلاق القوائم، قبول المهمة، إكمالها، التنبيه، الحفظ والخطأ.
- الحوار: أصوات الشخصيات، نطق عربي واضح، مستوى متسق، ومراجعة النطق والأسماء.
- الموسيقى: exploration، combat، boss، tension، victory، defeat، مع انتقالات لا تقطع المشهد فجأة.

### شروط القبول الصوتي

- لا clipping أو صمت غير مقصود أو قصّ حاد.
- مستوى متوازن بين الموسيقى والحوار والمؤثرات.
- تكرار بيئي غير مزعج، وطبقات عشوائية محدودة تمنع الرتابة.
- اختبار سماعات الهاتف ومكبره، وتغيير مستوى الصوت، وإيقاف/استئناف التطبيق.
- اختبار أحجام التحميل واستهلاك الذاكرة وعدد الأصوات المتزامنة.
- لا تستخدم صوتًا مستنسخًا أو صوت شخص حقيقي إلا بوجود الحقوق والموافقات اللازمة.

## 8. تدقيق الإضافات والأدوات الخارجية

### إضافات Godot الموجودة في الإعدادات

- `addons/ashen_asset_bridge`: افحص الكود كاملًا، وما يحمّله، ورسائل الأخطاء، وتعامل المسارات، وسلوك الإضافة عند غياب GLB.
- `addons/ashen_free_asset_pipeline`: تحقق من أن الجرد لا يغيّر الأصول أو يرفعها أو يتصل بالشبكة دون إعلان.
- `tools/generate_player_glb.py`: راجع التعامل مع الأسرار، وتنزيل الملفات، والتحقق من الاستجابة، والمهلات، والأحجام، والمسارات، وعدم الكتابة فوق ملف موجود دون موافقة.
- `tools/validate_free_assets.py`: اختبر الحالات السلبية: ملف بلا سجل، حقل ترخيص فارغ، ملف مفقود، امتداد غير معروف، وبيانات JSON غير صالحة.

### أدوات مقترحة حسب الوظيفة، وليست كلها مثبتة أو متصلة

- Blender: تنظيف النماذج، UV، الهيكل العظمي، التحريك، LOD، والتحقق من الهندسة.
- Krita أو أداة رسم مكافئة: مفاهيم الشخصيات والخرائط والأيقونات.
- Audacity: تنظيف الصوت وتحريره وفحص القمم.
- أداة فحص GLB/ glTF محلية: تحقق من بنية الملف والخامات والامتدادات.
- GitHub Actions: فحوص تلقائية لكل تغيير في الأصول والبيانات الوصفية.
- أدوات توليد خارجية مثل Meshy أو Tripo: تُستخدم فقط بعد مراجعة شروط التصدير والترخيص والتكلفة؛ لا تعتبر أيًا منها مثبتًا أو مستخدمًا في هذه الدفعة.

لا ترفع مفاتيح API أو رموز وصول أو مفاتيح توقيع داخل المستودع أو APK أو ملفات السجلات.

## 9. Android: الأداء والجودة

الهدف هو جودة مرئية متماسكة لا مجرد زيادة عدد المضلعات.

- نماذج بطبقات LOD عند الحاجة، مع خامات 1K/2K بحسب القياس الفعلي.
- ضغط ETC2/ASTC بحسب دعم الجهاز وجودة الصورة؛ اختبر كل إعداد بدل افتراض أفضلية واحدة.
- تقليل المواد والشفافية والظلال الديناميكية ومصادر الضوء النشطة.
- تجميع عناصر البيئة المتكررة عند ملاءمة المشهد، مع عدم التضحية بإمكانية الرؤية أو سهولة التعديل.
- أحجام ملفات وصوتيات مناسبة للتنزيل الأولي؛ يمكن فصل الحزم الاختيارية لاحقًا.
- اختبر على جهاز منخفض ومتوسط الأداء، لا على محاكي وحده.
- سجّل FPS/وقت الإطار، وذاكرة RAM/GPU إذا أمكن، ووقت التحميل، وحرارة الجهاز، وحجم APK/الحزمة، واختناقات الصوت.
- احتفظ بلقطات مقارنة من نفس الكاميرا والإضاءة والدقة قبل التغيير وبعده.

## 10. بوابات القبول

لا يقبل أي أصل نهائي إلا إذا اجتاز جميع البوابات ذات الصلة:

- **G0 — الهوية والمصدر:** مصدر وترخيص وحقوق إعادة توزيع موثقة.
- **G1 — سلامة الملف:** يفتح، لا مراجع مفقودة، وSHA-256 مسجل.
- **G2 — الجودة:** مراجعة فنية للنموذج أو الصورة أو الصوت.
- **G3 — الدمج:** يحمّل داخل المشهد الصحيح ولا يكسر اللعب أو واجهة المستخدم.
- **G4 — الأداء:** القياس على Android يفي بالميزانية المحددة للمشهد.
- **G5 — الانحدار:** الاختبارات الآلية ذات الصلة ناجحة على commit محدد.
- **G6 — قبول بصري/صوتي:** مراجعة بشرية موثقة ومقارنة قبل/بعد.
- **G7 — الإصدار:** بيانات المصدر والسجل والملفات والتراجع موثقة.

أي بوابة غير منفذة تسجّل «غير مختبرة»، لا «ناجحة».
