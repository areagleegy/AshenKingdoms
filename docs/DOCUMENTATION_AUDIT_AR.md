> النطاق: مراجعة تحريرية مبدئية لملفات README.md وdocs/README.md وdocs/PROJECT_STATUS_AR.md وdocs/DOCUMENTATION_GUIDE_AR.md. هذه ليست مراجعة شاملة لكل ملفات المصدر، ولا إثباتًا لتشغيل الاختبارات أو فحص كل رابط.

## 1. الخلاصة التنفيذية

التوثيق الأساسي منظم بالفعل: توجد نقطة دخول، ووثائق للرؤية والحالة والمعمارية والاختبار والبناء والشبكة والأصول وحزم المحتوى. كما يميز README وحالة التنفيذ بين النموذج الأولي والميزات التجريبية ومتطلبات الإنتاج.

الخطوة التالية ليست إنشاء نسخ مكررة من الوثائق الموجودة، بل تحسين إمكانية التحقق من الادعاءات، وربط كل نظام بأدلته، وإغلاق فجوات التوثيق بالتوازي مع تغييرات الكود.

## 2. ما تؤكده الملفات التي تمت مراجعتها

- README الرئيسي يوضح أن اللعبة نموذج أولي مبني على Godot 4.6 وGDScript، ويصرح بقيود Web والشبكة وحزم المحتوى.
- docs/README.md يعمل كفهرس ويوجه القارئ إلى مصادر الحقيقة ذات الصلة.
- docs/PROJECT_STATUS_AR.md يفصل بين الحالة المعروفة وما لم يثبت، ويحدد بوابات قبول Android وWeb والشبكة والأصول.
- docs/DOCUMENTATION_GUIDE_AR.md يحدد قواعد الصياغة، ومتى يجب تحديث الوثائق، وأوامر التحقق المحلي.
- توجد تعليمات لتشغيل اختبارات آلية ويدوية؛ ذكر الأمر في الوثائق لا يعني أنه نُفذ في هذه المراجعة.

## 3. قواعد الأدلة وحالة الميزات

استخدم التصنيفات التالية في جميع وثائق المشروع:

| التصنيف | معيار الاستخدام |
|---|---|
| موثق في المصدر | يوجد ملف أو إعداد محدد يدعم الادعاء؛ أضف مساره. |
| منفذ | يظهر السلوك في الكود أو الموارد الحالية. |
| اجتاز اختبارًا آليًا | يوجد اختبار محدد ونتيجة ناجحة مرتبطة بالـ commit المعني. |
| اجتاز اختبارًا يدويًا | سجل الجهاز/المتصفح والخطوات والنتيجة وتاريخ الاختبار. |
| تجريبي | يوجد تنفيذ، لكن لم تتحقق متطلبات الاعتمادية أو الأمان أو القبول كاملة. |
| مخطط | تصميم أو Issue أو وثيقة خطة؛ لا يوصف بأنه منفذ. |
| مؤجل/غير مدعوم | توجد فجوة معروفة أو قرار صريح بتأجيل الميزة. |

لا تستخدم «مكتمل» أو «جاهز للإنتاج» دون معايير قبول قابلة للقياس وأدلة قابلة للمراجعة.

## 5. بطاقة توثيق معيارية لكل نظام

عند إضافة نظام جديد أو تعديل نظام قائم، وثّق العناصر التالية بقدر انطباقها:

1. **الغرض والنطاق:** ما المشكلة التي يحلها النظام وما الذي لا يحله.
2. **الحالة:** منفذ، تجريبي، مخطط، مؤجل، أو غير مدعوم.
3. **نقاط الدخول:** أسماء المشاهد والسكربتات والموارد الفعلية.
4. **تدفق البيانات:** المصدر، التحقق، التعديل، التخزين، والمستهلكون.
5. **العقود:** الإشارات والدوال وواجهات البيانات والأحداث بين الأنظمة.
6. **الاعتماديات:** Godot والإضافات والحزم والخدمات الخارجية وإصداراتها عند الحاجة.
7. **الأمان:** حدود الثقة، والتحقق من المدخلات، والأسرار، وصلاحيات الملفات والشبكة.
8. **الأداء:** العمليات المتكررة، والتخصيصات، والتحميل، والذاكرة، ومقاييس القياس.
9. **الاختبارات:** اسم الاختبار، ما الذي يغطيه، وما لا يغطيه، ونتيجة التشغيل المرتبطة بالـ commit.
10. **الفشل والاستعادة:** السلوك عند انقطاع الشبكة أو فساد البيانات أو غياب المورد.
11. **القرارات المفتوحة:** أسئلة التصميم والمفاضلات والقيود المعروفة.
12. **سجل التغيير:** تاريخ التعديل وسبب التغيير والملفات المتأثرة.

## 6. بروتوكول تحديث الوثائق

1. افحص الكود والمشاهد وملفات الإعداد وملفات CI قبل تحرير وصف السلوك.
2. حدد الوثيقة المرجعية الوحيدة لكل موضوع، ثم حدّث الفهرس أو README فقط عند الحاجة.
3. اكتب الفارق بين الحالة الحالية والهدف المستقبلي صراحة.
4. حدّث الاختبارات أو وثّق الاختبار اليدوي اللازم إذا تغير السلوك.
5. شغّل من جذر المستودع:

~~~bash
python3 tools/validate_docs.py
python3 tools/validate_free_assets.py
git diff --check
~~~

6. شغّل اختبارات Godot وPython ذات الصلة، وسجّل الأوامر التي نُفذت فعلًا.
7. افحص نتائج GitHub Actions للـ commit نفسه قبل الدمج.
8. لا تعتبر تصدير APK أو Web أو نجاح اختبار loopback دليلًا على القبول على جهاز حقيقي أو الأمان على الإنترنت.
9. اجعل كل تغيير وثائقي في نفس Pull Request الذي غيّر الكود المرتبط به.
10. لا تضع أسرارًا أو مفاتيح توقيع أو رموز وصول في الوثائق أو سجلات الاختبار.

## 7. حدود هذه المراجعة

هذه الصفحة سجل تدقيق مبدئي وليست شهادة جودة أو أمان. لم يتم ضمن هذه المراجعة تشغيل Godot أو Python أو CI، ولم يتم اختبار اللعبة على جهاز Android أو متصفح فعلي. يجب عدم تسجيل أي من هذه الأنشطة على أنها مكتملة قبل تنفيذها وجمع أدلتها.
