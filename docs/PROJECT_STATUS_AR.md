# حالة تنفيذ ممالك الرماد

> آخر مراجعة تحريرية: 2026-10-19. هذه الصفحة ملخص للحالة وليست سجلًا حيًا لنتائج CI؛ تحقّق من تشغيل GitHub Actions المرتبط بالـ commit الذي تراجعه.

## ملخص المنصات والميزات

| المجال | الحالة المعروفة | ما لم يثبت بعد |
|---|---|---|
| اللعب الفردي | نموذج أولي قابل للتشغيل: حركة وقتال وصحة وأعداء وجرد وتدرج ومهمة تجريبية وحفظ محلي | القبول اليدوي الكامل والأداء على الأجهزة المستهدفة |
| الحوار وNPC والمهام | تنفيذ محلي تجريبي؛ أعلام الحوار تُحفظ ضمن الحفظ المحلي | التكامل مع ساحة الشبكة ومزامنة الحوار والمهام جماعيًا |
| اللعب الجماعي عبر ENet | ساحة مضيف/عميل تجريبية على Desktop وAndroid، مع اختبارات آلية بما فيها loopback | مصادقة إنتاجية، حفظ شبكي دائم، استضافة عامة آمنة، واختبار أجهزة وشبكات فعلية |
| Web | توجد سلسلة تصدير HTML5، ويضاف مسار الانضمام التجريبي عبر WebSocket | لم يثبت اتصال المتصفح بخادم منشور عبر WSS؛ لا يمكن للمتصفح استضافة الخادم، وما زال القبول الفعلي في المتصفح مطلوبًا |
| Android | ينتج CI APK اختباريًا لمعمارية ARM64 | توقيع الإنتاج، قرار قناة التوزيع، واختبار قبول موثق على هاتف فعلي |
| تنزيل حزم المحتوى | توجد بنية برمجية أولية للفهرس والتوقيع والتحقق والتثبيت | التنزيل الإنتاجي مؤجل ومعطل افتراضيًا؛ لا توجد خدمة توزيع إنتاجية معدّة |
| الأصول الفنية | يوجد سجل آلي للمصادر والتراخيص؛ راجع assets/asset_manifest.json وdocs/ASSET_CREDITS.md | السجل لا يثبت اكتمال مجموعة فنية نهائية؛ لا يُفترض وجود player.glb أو صوتيات نهائية دون ملفات فعلية وسجل ترخيص |
| التحقق والبناء | GitHub Actions يتضمن سير عمل للتحقق وسير عمل لتصدير Android/Web | يجب فحص نتيجة كل تشغيل وملف commit بعينه؛ النجاح لا يثبت القبول اليدوي |

## قرارات الإصدار المعتمدة

- الهدف هو اللعب الفردي والجماعي.
- المنصتان المستهدفتان هما Android وWeb.
- المطلوب إضافة أصول جديدة مجانية ومفتوحة الترخيص مع توثيق المصدر وشروط الاستخدام والإسناد.
- تنزيل المحتوى الاختياري مؤجل ويبقى معطلًا في الإصدار المقصود.
- لا يتم الدمج قبل مراجعة نتيجة CI للـ PR؛ لا تُسجّل نتيجة اختبار إلا إذا نُفذ فعليًا.

راجع [نطاق الإصدار المعتمد](RELEASE_SCOPE_AR.md) للتفاصيل وبوابات القبول.

## معنى حالة CI

اعتبر CI دليلًا فقط على الخطوات التي نفّذها التشغيل على commit المحدد. عند المراجعة:

1. افتح تشغيلَي Validate Godot Project وBuild Android and Web المرتبطين برأس PR.
2. تحقق من الحالة النهائية لكل Job ومن الخطوات الفاشلة أو المتخطاة.
3. تحقق من وجود Artifact إذا كان البناء يفترض أن ينتجه، ومن اسمه وcommit المصدر.
4. سجل رابط التشغيل والـ commit في PR أو سجل الإصدار عند الحاجة.
5. لا تعتبر Artifact دليلًا على اختبار جهاز حقيقي أو على توقيع إنتاجي.

## بوابات القبول المتبقية

- [ ] تثبيت APK حديث على هاتف Android حقيقي وتسجيل طراز الجهاز وإصدار النظام والنتيجة.
- [ ] نشر تصدير Web عبر HTTP/HTTPS واختباره في المتصفحات وأحجام العرض المستهدفة.
- [ ] اختبار مسار WebSocket من متصفح فعلي إلى خادم WebSocket منشور عبر WSS، مع التحقق من الاتصال والفصل والمزامنة قبل إعلان دعم Web الجماعي.
- [ ] مراجعة مصدر ورخصة وإسناد كل أصل خارجي في النسخة الموزعة.
- [ ] تحديد هوية التطبيق وإصدار Android وقناة التوزيع والتوقيع الآمن.
- [ ] حفظ قرار قبول/قبول مشروط/رفض مستند إلى الأدلة.

لا تغلق بوابة الإصدار لمجرد أن جميع فحوص CI خضراء. راجع [Issue #20 — Release gate](https://github.com/areagleegy/AshenKingdoms/issues/20)، و[مهمة دعم اللعب الجماعي على Web](https://github.com/areagleegy/AshenKingdoms/issues/21)، و[مهمة الأصول المفتوحة الترخيص](https://github.com/areagleegy/AshenKingdoms/issues/22).
