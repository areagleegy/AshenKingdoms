## النتائج ذات الأولوية

### P0 — الوصول وصحة الادعاءات
- توجيه القارئ من README إلى التشغيل والحالة والنطاق والاختبارات بأقل عدد من النقرات.
- الفصل الصريح بين الرؤية المستقبلية والحالة الفعلية ونتيجة الاختبار.
- ذكر التاريخ والوقت والمنطقة الزمنية والـcommit في كل لقطة متغيرة.
- نجاح CI لا يثبت اختبار APK على جهاز حقيقي أو أمان الشبكة العامة أو جاهزية الإنتاج.

### P1 — التداخل
- `OPEN_WORK_REGISTER_AR.md` و`ISSUE_AUDIT_AR.md` و`PR_REVIEW_DEPENDENCIES_AR.md` تتقاطع في بيانات GitHub لكن لكل منها غرض مختلف: لقطة، تحليل مخاطر، واعتماد بين الفروع.
- `CONTINUITY.md` و`SESSION_HANDOFF_AR.md` يتداخلان: الأول سجل قرار/دليل، والثاني ملخص استئناف.
- `DOCUMENTATION_AUDIT_AR.md` يسجل العيوب والإجراءات؛ `REPOSITORY_DOCUMENTATION_MAP_AR.md` يربط الأنظمة بمصادر الحقيقة.
- لا تحذف الخطط والمواصفات المؤرخة لمجرد قدمها؛ اربطها بالحالة الفعلية.

### P2 — معيار موحد
- غرض ونطاق وحدود وروابط صحيحة لكل وثيقة.
- أوامر قابلة للنسخ مع المتطلبات والمنصة.
- كل نتيجة اختبار مرتبطة بالاسم والـcommit والنتيجة والدليل.
- إبقاء أسماء الملفات والواجهات البرمجية كما هي، والشرح الأساسي بالعربية.
- تجنب اعتماديات توثيق جديدة إذا كانت أدوات Python وCI الحالية كافية.

## سياسة الحذف وإعادة التسمية

قبل أي حذف: اقرأ الملف كاملًا، وقارنه بالبديل، وابحث عن كل الإشارات والروابط، وانقل المحتوى الفريد، وحافظ على سجل القرارات، ثم شغّل مدقق الوثائق والاختبارات ذات الصلة. نفّذ الحذف أو إعادة التسمية في PR مستقل؛ لا حذف جماعي غير قابل للمراجعة.
