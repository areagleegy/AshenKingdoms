# مراجعة حوكمة AshenKingdoms — تجميع Parts 14–18 وما يتصل بها

- **الإصدار:** 1.0
- **تاريخ الإعداد:** 2026-10-24
- **الحالة:** مراجعة توثيقية مقترحة؛ لا تعني اعتمادًا تنفيذيًا أو اجتياز اختبارات
- **المستودع:** [areagleegy/AshenKingdoms](https://github.com/areagleegy/AshenKingdoms)
- **الغرض:** تنظيف التداخل بين أجزاء الحوكمة، وتوحيد المصطلحات والتتبّع، وتحديد فجوات التحقق، وربط القرارات بمصادر الحقيقة.

> **حدود المراجعة:** أُعدّ هذا المستند من نصوص Parts المتاحة في سياق العمل، ومن ملفات README وفهرس الوثائق وحالة التنفيذ وخريطة التوثيق وسجل العمل المفتوح التي جرى الاطلاع عليها في المستودع. لم يتسنَّ إثبات أن كامل ملف `DeepSeek - إلى المجهول.pdf` قد استُخرج أو قُرئ هنا؛ لذلك لا يُقدَّم هذا التقرير على أنه مراجعة كاملة لذلك الملف أو لكل تاريخ المحادثات. كما أن حالة GitHub والاختبارات قابلة للتغير ويجب إعادة فحصها قبل اتخاذ قرار تنفيذي.

## 1. الخلاصة التنفيذية

تغطي Parts 14–18 خمسة محاور متكاملة: تشغيل الأمن، والتدقيق ومعالجة النتائج، واختبارات الأمن، وإدارة المخاطر والقرارات، وضبط التغيير والمتطلبات، ثم شريحة اللعب الأولى. الفكرة العامة متماسكة: لا يكفي وجود سياسة أو ملف؛ يجب أن توجد مسؤولية واختبارات وأدلة ومراجعة ومعايير إغلاق.

لكن النصوص المتداولة تستخدم أرقام Parts بصورة غير مستقرة: **Part 14** استُخدم للأمن التشغيلي ولإدارة المعرفة ولإدارة المخاطر؛ **Part 15** استُخدم للتدقيق ولإدارة المخاطر؛ **Part 16** استُخدم لاختبارات الأمن، مع ذكر سابق له كإدارة التغيير؛ وPart 17 للمتطلبات؛ وPart 18 للشريحة القابلة للعب. هذا تضارب في الترقيم والفهرسة، لا يلزم أن يكون تضاربًا في الأفكار.

**التوصية:** الحفاظ على النصوص الأصلية في الأرشيف لأغراض التتبع، واعتماد فهرس موحد بالأسماء لا بالأرقام وحدها، ثم ترحيل كل جزء إلى ملف مرجعي واحد. لا تعاد تسمية الملفات القديمة أو استبدالها جماعيًا قبل التحقق من الروابط والـ PRs المفتوحة.

## 2. مصدر الحقيقة ودرجات الثقة

ترتيب الأدلة عند تعارض الادعاءات:

1. الكود وموارد Godot وملفات `.github/workflows/` لتحديد التنفيذ وخطوات CI الفعلية.
2. نتائج الاختبارات وسجلات Actions المرتبطة بالـ commit المحدد.
3. Issues وPull Requests للمقاصد والنطاق والقرارات المكتوبة، مع فحص حالتها الحالية.
4. الوثائق النشطة لتفسير النظام والإجراءات.
5. وثائق الخطط والمحادثات والملفات المؤرشفة للسياق التاريخي، لا لإثبات التنفيذ.

استخدم حالات واضحة في جميع التقارير:
- **مقترح:** لم يعتمد.
- **معتمد تصميميًا:** قرار موثق، وليس إثبات تنفيذ.
- **منفذ:** تغيّر الكود/الملف.
- **متحقق آليًا:** اختبار أو CI نجح على commit محدد.
- **متحقق يدويًا:** اختبار موثق على البيئة/الجهاز المعني.
- **مقبول للإصدار:** اجتازت جميع بوابات القبول المعلنة.
- **مؤجل/مرفوض/متقاعد:** حالة صريحة مع سبب ومالك وتاريخ مراجعة عند الحاجة.

لا تُستخدم كلمة «نجح» أو «مكتمل» بلا دليل قابل لإعادة الفحص.

## 4. نتائج المراجعة والتصحيح

### 4.1 نقاط قوة يجب الاحتفاظ بها

- ربط كل نتيجة بمالك وحالة ودليل ومعايير إغلاق.
- الفصل بين المعالجة والتحقق والإغلاق؛ منفذ الإصلاح ليس بالضرورة هو المراجع المستقل.
- اشتراط اختبار انحدار للثغرات المغلقة.
- تمييز الاختبار الآلي عن قبول Android الفعلي.
- اعتماد تغييرات صغيرة قابلة للتراجع بدل إعادة كتابة واسعة.
- وضع معايير قبول قابلة للقياس للشريحة الأولى.
- اعتبار الافتراضات غير المتحققة مخاطر، وتسجيل الاستثناءات بتاريخ انتهاء وخطة خروج.

### 4.2 تناقضات تحتاج إلى حسم

1. **تكرار أرقام الأجزاء:** Part 14 و15 و16 تشير إلى مواضيع مختلفة في النصوص المقدمة. أصلح الفهرس والروابط قبل إعادة التسمية.
2. **تكرار سجلات النتائج:** تظهر أسماء مثل `reports/FINDINGS_REGISTER.md` و`FINDINGS_REGISTER.md` دون حسم المسار القياسي. اختر موقعًا واحدًا؛ يُفضّل اتباع الهيكل الحالي في المستودع بدل إنشاء جذور موازية.
3. **تكرار سجل المخاطر:** ورد `docs/RISK_REGISTER.md` وأيضًا `RISK_REGISTER.md`. اجعل `docs/RISK_REGISTER.md` المسار القياسي إن لم يوجد ملف قائم آخر له مستهلكون، ثم أضف رابط توافق أو ترحيلًا موثقًا.
4. **أسماء أدلة التدقيق:** ورد `AUDIT_REPORT.md` و`reports/AUDIT_REPORT.md` و`AUDIT_DASHBOARD.md` دون مسار موحد. حدّد مكانًا مرجعيًا واحدًا وروابط فهرسة بدل نسخ الملفات.
5. **حالة «FROZEN»:** تعني تجميد إطار الوثيقة، لا تجميد جميع تطبيقات المشروع. أضف هذا التوضيح لتجنب اعتبار الضوابط منفذة أو منع إصلاحات لازمة.
6. **اختبار `get_var(true)`:** لا تشغّل اختبارًا هجوميًا على بيانات موثوقة أو على بيئة إنتاج. اجعل الاختبار محصورًا ببيانات اختبار معزولة، واختبر أن مسار الإنتاج يستخدم `get_var(false)` عند التعامل مع ملفات غير موثوقة. يجب أن يكون معيار النجاح هو رفض الحمولة غير الموثوقة دون تنفيذ كود أو انهيار، لا مجرد إعادة إنتاج الاستغلال.
7. **تفسير «Unknown Fields»:** رفض كل حقل إضافي قد يعوق تطور المخطط. وثّق سياسة صريحة: رفض الحقول غير المعروفة أو تجاهلها وفق نسخة المخطط، مع اختبارات ترحيل وتوافق. لا تترك القرار ضمنيًا.
8. **الكتابة الذرية:** تسلسل «Temp → Write → Verify → Rename» يحتاج تفاصيل تشغيلية: الكتابة إلى ملف مؤقت في المجلد نفسه، فحص النتيجة، المحافظة على آخر حفظ سليم، التعامل مع فشل إعادة التسمية، وتنظيف المؤقتات. لا تدّعِ ذرية متكاملة عبر كل نظام ملفات دون اختبار المنصة.
9. **اختبارات الشبكة:** حدود السرعة وnonce/timestamp والتصحيح السلطوي تحتاج تعريفات دقيقة لمصدر الوقت، ونافذة صلاحية الرسالة، وربط nonce باللاعب/الجلسة/الإجراء، وسلوك إعادة الاتصال. لا تعدّ loopback دليلًا على أمان الإنترنت.
10. **شريحة v0.7:** النص يطلب «APK موقّعًا» لكنه لا يميز توقيع اختبار عن توقيع توزيع إنتاجي. افصل بين APK تجريبي، وتوقيع release، وإدارة المفتاح خارج المستودع، واختبار الجهاز الفعلي.
11. **مقاييس الأداء:** هدف 60 FPS لا يكفي وحده؛ سجّل الجهاز، إصدار Android، الدقة، إعدادات الرسوم، مدة القياس، متوسط/وسيط/ذيل frame time، الذاكرة، زمن التحميل، وحرارة الجهاز إن توفرت.
12. **إغلاق F-001:** لا يمكن تأكيد إغلاقه من الوثيقة وحدها. يلزم ربط المعرّف بسجل findings الفعلي، والـ commit، والاختبار، وسجل CI، وموافقة المراجع.

## 5. النموذج التشغيلي الموحد

استخدم السلسلة التالية لكل خطر أو نتيجة:

`Observation → Risk/Finding → Owner → Action → Test → Evidence → Independent Review → Closure → Regression Protection`

قواعد التنفيذ:
- كل Finding لها ID ثابت، وشدة، وفئة، ووصف قابل للتحقق، ومالك، ودليل، وحالة، وتاريخ/موعد مستهدف.
- كل Risk له احتمال وأثر ودرجة ومالك وتخفيف وخطة طوارئ وتاريخ مراجعة وحالة.
- كل Change له سبب ونطاق وتأثير ومخاطر وخطة رجوع واختبارات وموافقة.
- كل Requirement له هدف ومعايير قبول وروابط إلى Issue/Implementation/Test/Evidence.
- كل Evidence يشير إلى commit وبيئة وأمر الاختبار ونتيجة فعلية وتاريخ؛ لا تُخزّن الأسرار أو البيانات الحساسة.
- لا يُغلق بند أمني دون تحقق مستقل أو مبرر استثناء معتمد ومؤقت.
- لا تُحذف سجلات العناصر المتقاعدة؛ احتفظ بالسجل التاريخي وسبب القرار.

## 6. مصفوفة التتبّع المطلوبة

| الكيان | المصدر القياسي المقترح | الروابط الإلزامية |
|---|---|---|
| Requirement | Issue أو سجل متطلبات مفهرس | الهدف، القبول، التنفيذ، الاختبار، الدليل |
| Change | Pull Request + ADR عند التغيير المعماري | Issue، المخاطر، الموافقة، الاختبارات، الرجوع |
| Finding | سجل نتائج مركزي واحد | دليل، مالك، معالجة، تحقق، اختبار انحدار |
| Risk | `docs/RISK_REGISTER.md` | مالك، درجة، تخفيف، طوارئ، مراجعة |
| Security Debt | سجل ديون أمني واحد | سبب التأجيل، الخطر، المالك، موعد المراجعة |
| Exception | سجل استثناءات | المبرر، المراجع، تاريخ الانتهاء، خطة الخروج |
| Evidence | تقارير الاختبار وCI المرتبطة بالـ commit | الأمر، البيئة، النتيجة، وقت التنفيذ |
| Asset/Dependency | سجل الأصول والتبعيات | المصدر، الإصدار، الرخصة، الإسناد، فحص سلسلة التوريد |
| Release Gate | `docs/RELEASE_SCOPE_AR.md` وخطة الاختبار | بناء، CI، قبول يدوي، تراخيص، توقيع، قرار الإصدار |

هذه أسماء معيارية مقترحة؛ قبل إنشاء سجلات جديدة، تحقّق من الملفات القائمة وادمج التكرار بدل صنع مصادر حقيقة متوازية.

## 9. قرار المراجعة

**القرار الحالي: قبول توثيقي مشروط، وليس اعتمادًا تنفيذيًا.**

الأجزاء المقدمة تشكل إطارًا مفيدًا، لكنها تحتاج إلى تثبيت الترقيم، وتوحيد مسارات السجلات، وفصل الحالة التصميمية عن التنفيذ المثبت، وربط الإغلاق بأدلة فعلية. لا يُنصح بدمج تغييرات كود واسعة ضمن هذا التعديل التوثيقي؛ اجعل إصلاحات الكود واختبارات الأمن تغييرات صغيرة منفصلة، كل منها بحدود نطاق واضحة وCI ومراجعة مستقلة.

## سجل التغييرات

- 2026-10-24: إنشاء تجميعة مراجعة لأجزاء الحوكمة 14–18 من النصوص المتاحة ومصادر المستودع المقروءة؛ أضيفت قواعد توحيد المصطلحات، وتناقضات تحتاج إلى حسم، وخطة عمل مرتبة، ومراجع أولية.
