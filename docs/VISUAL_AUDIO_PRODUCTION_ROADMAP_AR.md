# خارطة إنتاج المرئيات والصوتيات — AshenKingdoms

**الأولوية:** Android أولًا، مطوّر واحد، Godot 4.6، مشروع مفتوح المصدر.  
**قاعدة التنفيذ:** فرع مستقل لكل مرحلة، مراجعة PR، لا تغيير مباشر على `main`، ولا ادعاء نجاح اختبار لم يُشغّل.

## الرؤية الفنية

الهوية المقترحة: فانتازيا قاتمة ذات ملمس واقعي؛ رماد ورياح وآثار استخدام على المعدات، ضوء مقروء، خامات خشب وحجر ومعدن وجلد، وألوان محصورة تساعد اللاعب على تمييز التهديدات والتفاعل. الخيال يظهر في الإضاءة والرموز والسحر والتصميم، مع بقاء الحركة والمواد والأحجام متسقة. يجب أن تظل الصورة واضحة على شاشة هاتف صغيرة.

## خريطة الحزم

| الحزمة | المحتوى | معيار الخروج |
|---|---|---|
| A0: تدقيق | جرد الملفات، hashes، المراجع المكسورة، التراخيص، الإضافات، خط أساس CI | تقرير قابل لإعادة التنفيذ؛ لا أصول مجهولة تُعتمد |
| A1: معيار فني | لوحة ألوان، مراجع، مقياس، كثافة تفاصيل، ميزانيات مثلثات/خامات، إعدادات استيراد | صفحة مواصفات مرئية وصوتية مع عينة معتمدة |
| A2: بطل عمودي | لاعب واحد، هيكل عظمي، idle/walk/run/attack/hit/death، خامات، سلاح أساسي | لا اختراقات خطرة، تحكم سليم، أداء مقبول على Android |
| A3: مجموعة البيئة الأولى | منطقة لعب واحدة متماسكة: أرض، صخور، نباتات/رماد، مبنى، إضاءة، ضباب، sky | مشهد قابل للعب، تصادم وملاحة واضحة، لا مراجع مفقودة |
| A4: أعداء ومعدات | عدو عادي واحد ثم عدو نخبة؛ ملابس ودروع وأسلحة متوافقة | دورة قتال مكتملة واختبارات hitbox ومزامنة الأنيميشن |
| A5: الصوت | طبقات بيئية، خطوات سطحية، قتال، واجهة، موسيقى قصيرة وحوار تجريبي | توازن مستويات، لا clipping، قابلية كتم وضبط الصوت |
| A6: المؤثرات | شرر معدني، غبار/رماد، ضربة، سحر محدود، أثر إصابة | وضوح بصري دون حجب قراءة القتال أو تجاوز ميزانية الأداء |
| A7: توسعة المحتوى | خرائط/مناطق إضافية، تنويعات أعداء، أسلحة، ملابس، حوار | الالتزام بمعيار الأصول المعتمد وإعادة استخدام الموارد |
| A8: حزم اختيارية | تجميع المحتوى، توقيع، تنزيل آمن، ترقية/تراجع، فحص المساحة | اختبار أمان وسلامة على جهاز Android، مع بقاء التنزيل معطلًا حتى اكتمال الخدمة |
| A9: قبول الإصدار | أداء، جودة، تراخيص، CI، اختبار أجهزة، تدقيق التراجع | جميع البوابات المطلوبة موثقة ومؤرخة |

## تنظيم المجلدات المقترح

يُستخدم هذا الهيكل كهدف تنظيمي، ولا يُنشأ مجلد فارغ بوصفه أصلًا مكتملًا:

```text
assets/
  characters/
    player/
    npcs/
    enemies/
    bosses/
  equipment/
    weapons/
    armor/
    clothing/
    shields/
  environments/
    regions/
    modular/
    props/
    vegetation/
    sky/
  materials/
    master/
    surfaces/
    decals/
  animation/
    humanoid/
    creatures/
  audio/
    music/
    ambience/
    sfx/
    voice/ar/
  vfx/
  ui/
  video/cinematics/
  references/            # لا تُوزع مراجع غير مرخصة ضمن اللعبة
```

كل أصل يحتاج إلى سجل مستقل في `assets/asset_manifest.json`، ويجب أن يظل ملف المصدر والرخصة قابلين للتتبع.

## نموذج بيانات لكل أصل

- `asset_id`: معرف ثابت.
- `path`: مسار المستودع.
- `category` و`intended_use`: فئة الأصل واستخدامه.
- `source_url`, `author`, `license`, `license_url`, `attribution`.
- `commercial_use`, `redistribution_allowed`, `modification_allowed`: قيم موثقة لا تخمينية.
- `sha256`, `file_size_bytes`, `created_or_acquired_at`.
- بيانات فنية حسب النوع: مثلثات/مواد/خامات/عظام/حركات أو مدة/عينة/قنوات/مستوى صوت.
- `godot_import_settings`, `used_by`, `android_test_device`, `acceptance_status`, `review_notes`.

لا تغيّر schema الحالي دون تحديث أداة التحقق واختبارها؛ هذه الحقول مواصفة مستهدفة وليست ادعاءً بأن المخطط الحالي يدعمها كلها.

## ميزانيات أولية قابلة للقياس

هذه أهداف بدء وليست نتائج أداء مقاسة، وتُعدّل بعد الاختبار:

- بطل اللاعب: 8k–20k مثلث للنموذج الأساسي، خامة أو اثنتان بدقة 1K مبدئيًا.
- عدو عادي: 5k–15k مثلث كهدف أولي.
- خامات البيئة: تفضيل خامات مشتركة؛ 1K/2K حسب حجم العنصر ومسافة الكاميرا.
- مؤثرات الجسيمات: عدد قليل من الأنظمة المتزامنة في القتال، مع سقف يحدد بعد القياس.
- الصوت: OGG أو صيغة مضغوطة مناسبة للمحتوى الطويل، وWAV فقط حيث تبرر الحاجة؛ قارن الجودة والحجم على الأجهزة.
- الأداء: استهدف 30 FPS مستقرًا على الجهاز الأدنى المستهدف كخط أساس أولي، ثم قرر هل توجد أجهزة يمكنها تحقيق 60 FPS. سجّل الدقة وحرارة الجهاز ومدة الاختبار.

لا تُستخدم الأرقام أعلاه لإعلان الجاهزية قبل قياسها.

## توزيع العمل لمطوّر واحد

- 40% من الوقت: تنفيذ الأصل/المشهد الأساسي.
- 25%: الدمج في Godot وضبط الخامات والأنيميشن والصوت.
- 20%: اختبار Android والأداء وتصحيح العيوب.
- 10%: التراخيص والتوثيق والـ manifests.
- 5%: مراجعة النتائج وخطة التراجع.

النسب إرشادية؛ لا تبدأ مرحلة جديدة إذا كانت بوابة المرحلة الحالية فاشلة.

## بوابات جودة ثابتة

1. لا أصل دون ترخيص واضح.
2. لا نموذج دون فحص هندسي/هيكل/خامات.
3. لا صوت دون مراجعة استماع وقياس.
4. لا دمج دون فتح المشهد واختبار المسار المرتبط به.
5. لا تحسين أداء دون قياس قبل/بعد على نفس الجهاز والإعدادات.
6. لا تعديل مباشر على `main`.
7. لا نتيجة اختبار بلا رابط CI أو سجل أمر وتاريخ وcommit SHA.
8. لا تعتمد على صورة توليد بوصفها نموذجًا ثلاثي الأبعاد، ولا على ملف GLB بوصفه شخصية متحركة ما لم يثبت ذلك بالفحص.

## مصفوفة اختبار القبول

| المستوى | الفحص | الدليل |
|---|---|---|
| آلي | `python3 tools/validate_docs.py` | سجل الأمر والنتيجة |
| آلي | `python3 tools/validate_free_assets.py` | سجل فحص manifest |
| آلي | `godot --headless --path . --editor --quit` | مخرجات الاستيراد/الأخطاء |
| آلي | اختبارات المشروع المذكورة في `docs/TEST_PLAN.md` | روابط CI على SHA المعني |
| بصري | مراجعة اللاعب والملابس والأسلحة والبيئة في Godot | لقطات ثابتة وملاحظات |
| صوتي | استماع على سماعة الهاتف ومكبره | قائمة قبول وملاحظات |
| جهاز | تثبيت APK وتشغيل المسار الأساسي | طراز الجهاز، Android، commit، النتائج |
| أداء | FPS/وقت إطار/تحميل/ذاكرة/حرارة | قياسات قابلة للمقارنة |
| قانوني | مراجعة المصدر والترخيص والإسناد | روابط المصدر ونص الرخصة وسجل القرار |

## ترتيب التنفيذ الموصى به

1. إكمال جرد الملفات ونتائج الترخيص قبل شراء أو توليد أي أصول.
2. اعتماد style guide وميزانيات الأداء.
3. إنتاج بطل واحد وسلاح واحد وعدو واحد.
4. إنتاج منطقة واحدة مصقولة وقابلة للعب بدل خرائط كثيرة غير متناسقة.
5. بناء مجموعة صوتية قصيرة تغطي الحلقة الأساسية.
6. قياس Android وإصلاح الاختناقات.
7. تعميم المعيار على بقية الأصول.
8. لا تفتح تنزيل حزم المحتوى للمستخدمين حتى اكتمال التوقيع والتحقق من سلامة الحزم والاسترجاع واختبارات الجهاز.

## خارج النطاق حتى إشعار آخر

- لا توليد مدفوع تلقائيًا.
- لا مفاتيح API في المستودع.
- لا استبدال جماعي للأصول قبل اعتماد عينة.
- لا وعد بدعم Web multiplayer أو أداء 60 FPS أو مظهر واقعي فوتوغرافي دون تنفيذ وقياس.
- لا دمج تلقائي لهذه الخطة في `main`.
