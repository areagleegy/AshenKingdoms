# دليل كتابة وصيانة وثائق ممالك الرماد

## الغرض

تجعل هذه القواعد وثائق المشروع قابلة للتنقل والمراجعة، وتمنع الخلط بين الخطة، والتنفيذ الموجود في المستودع، والاختبار الذي أُجري فعلًا، والجاهزية الإنتاجية.

## خريطة مصدر الحقيقة

| السؤال | المصدر الأساسي |
|---|---|
| ما نطاق الإصدار المستهدف؟ | docs/RELEASE_SCOPE_AR.md |
| ما الذي يعمل حاليًا وما القيود؟ | docs/PROJECT_STATUS_AR.md مع الرجوع إلى الكود |
| كيف تعمل الأنظمة؟ | docs/TECHNICAL_ARCHITECTURE.md والكود الفعلي |
| كيف يتم تشغيل الشبكة وما مخاطرها؟ | docs/NETWORKING.md وscripts/ |
| ما الاختبارات المطلوبة؟ | docs/TEST_PLAN.md و.github/workflows/validate.yml |
| كيف تُبنى المنصات؟ | docs/BUILD_ANDROID_WEB_AR.md و.github/workflows/build.yml |
| ما ترخيص الأصول؟ | assets/asset_manifest.json وdocs/ASSET_CREDITS.md، مع قراءة نص الترخيص الأصلي |
| كيف تُجهز حزم المحتوى؟ | content/README.md وكود scripts/content/ |

عند التعارض، يكون التنفيذ في الكود وملفات سير العمل هو المرجع للسلوك الحالي. سجّل عدم التطابق في PR وصحح الوثيقة ذات الصلة بدل نسخ وصف غير متحقق إلى وثائق أخرى.

## قواعد الصياغة

- استخدم العربية في وثائق التشغيل والإجراءات الموجهة لمساهمي المشروع؛ أبق أسماء السكربتات والعقد والأوامر كما هي في الكود.
- ابدأ كل وثيقة بهدف واضح، وحدد ما إذا كانت تصف الحالة الحالية أم خطة مستقبلية.
- استخدم أوصافًا دقيقة مثل «موجود»، «تجريبي»، «مؤجل»، «غير مدعوم حاليًا»، و«تم التحقق في CI». تجنب «مكتمل» أو «جاهز للإنتاج» دون معايير قبول وأدلة.
- اذكر إصدار Godot والأدوات عند تأثيرها على النتائج.
- اكتب الأوامر على أساس التشغيل من جذر المستودع، واذكر متطلبات النظام إذا لم تكن عامة.
- استخدم روابط Markdown نسبية للملفات داخل المستودع، واختبرها. احتفظ بالروابط الخارجية في المصادر الرسمية قدر الإمكان.
- لا تخزّن مفاتيح API أو كلمات المرور أو ملفات التوقيع أو سجلات تحتوي أسرارًا داخل الوثائق.
- عند الاعتماد على خدمة خارجية تتغير خططها أو حصصها أو شروطها، لا تجعل الأرقام المتغيرة حقيقة ثابتة؛ أشر إلى صفحة الشروط الرسمية واطلب مراجعتها وقت الاستخدام.
- لا تصف أصلًا بأنه مفتوح الترخيص لمجرد أنه مجاني للتنزيل. وثّق الترخيص الفعلي وشروط الاستخدام التجاري والتعديل وإعادة التوزيع والإسناد.

## متى تُحدّث الوثائق؟

حدّث الوثائق في نفس PR الذي يغيّر:
- المشاهد أو نقاط بدء المشروع أو مسؤوليات السكربتات.
- سلوك الحفظ أو الحوار أو المهام أو الجرد أو الشبكة.
- خطوات الاختبار أو أوامر CI أو إصدارات الأدوات.
- إعدادات التصدير أو المنصات أو أسماء Artifacts.
- مصادر الأصول أو بيانات الترخيص أو سياسة تنزيل المحتوى.

لا تنسخ تفاصيل كل نظام إلى README والفهرس معًا. اجعل README.md مقدمة قصيرة، وdocs/README.md فهرسًا، وصفحة النظام هي مرجع التفاصيل.

## قائمة التحقق لمراجعة وثائق PR

- [ ] الوصف مطابق للتنفيذ الحالي ولا يصف خطة كأنها ميزة موجودة.
- [ ] الروابط الداخلية صحيحة والملفات المشار إليها موجودة.
- [ ] الأوامر والمسارات وأسماء الموارد مطابقة للمستودع.
- [ ] نتائج الاختبار موصوفة بدقة، مع التفريق بين الآلي واليدوي.
- [ ] الأصول الخارجية لها مصدر ورخصة وإسناد واضح.
- [ ] لا توجد أسرار أو بيانات مستخدم في الأمثلة أو سجلات الاختبار.
- [ ] تم تشغيل python3 tools/validate_docs.py؛ وشُغّل python3 tools/validate_free_assets.py عند تغيير سجل الأصول أو ملفاتها.
- [ ] فحوص CI على رأس PR اكتملت بنجاح قبل الدمج.

## التحقق المحلي

من جذر المستودع بعد تثبيت Python 3، شغّل:

~~~bash
python3 tools/validate_docs.py
python3 tools/validate_free_assets.py
git diff --check
~~~

الأمران الأول والثاني يتحققان من الوثائق وسجل الأصول وفق قواعد المشروع. الأمر الثالث يتحقق من المسافات وأخطاء diff الشائعة. لا تغن هذه الأوامر عن فحص CI الكامل أو اختبارات الجهاز والمتصفح اليدوية.

## تحديث سجل الحالة

حدّث docs/PROJECT_STATUS_AR.md عند تغير حالة ميزة أو منصة جوهريًا. لا تضع فيه نتائج CI دائمة على أنها الحالة الحالية؛ اربط بالـ workflow والـ commit المحددين، لأن نتيجة التشغيل تتغير مع كل تحديث.


## 9. التوثيق الشامل وسجل الاستمرارية

استخدم المراجع القائمة بدل إنشاء وثائق متكررة:

- [خريطة التوثيق الشامل](REPOSITORY_DOCUMENTATION_MAP_AR.md): تحدد موضع توثيق النظام، ملفاته، واختباراته والفجوات.
- [سجل الاستمرارية](CONTINUITY.md): نقطة الاستئناف وقرارات التطوير والقيود طويلة الأجل.
- [فهرس سياق المحادثات](CONVERSATION_CONTEXT_ARCHIVE_AR.md): الموضوعات والقرارات الواردة في سياق المحادثات المتاح، وليس تفريغًا حرفيًا.
- [دليل تسليم الجلسة](SESSION_HANDOFF_AR.md): الخطوات العملية عند استئناف العمل.
- [سجل العمل المفتوح](OPEN_WORK_REGISTER_AR.md): لقطة مؤرخة لقضايا وطلبات دمج GitHub؛ يجب إعادة جلب البيانات عندما تتغير الحالات.
- [تدقيق Issues وPRs](ISSUE_AUDIT_AR.md): قراءة المخاطر وبوابات الإصدار، مع الانتباه إلى تاريخ كل لقطة.

### قواعد تحديث هذه الوثائق

1. حدّث الوثيقة الأساسية للنظام المتأثر أولًا، ثم حدّث الفهرس عند الحاجة.
2. سجّل كل نتيجة اختبار مع SHA الخاص بالالتزام ورابط التشغيل وحالته النهائية.
3. ميّز بين خطة مستقبلية وتغيير منفذ ونجاح CI وقبول يدوي.
4. لا تسجل حالة PR على أنها جزء من `main` قبل تأكيد الدمج.
5. لا تحفظ في الأرشيف بيانات اعتماد أو رموز وصول أو مفاتيح توقيع.
6. إذا كان المطلوب حفظ المحادثات كاملة، احتفظ بتصدير ChatGPT الأصلي والمرفقات مستقلة؛ الملخصات داخل المستودع لا تستعيد الرسائل أو الملفات المفقودة.
