# مصفوفة اختبار اللعبة الشاملة — Ashen Kingdoms

- تاريخ إعداد الخطة: 2026-10-23
- الفرع المرجعي للمراجعة: main
- محرك اللعبة: Godot 4.6
- المنصات: Android ARM64 وWeb؛ الشبكة ENet تجريبية وليست مفعلة على Web.
- نوع المستند: خطة اختبار قابلة للتنفيذ. لا تعني البنود نجاحًا حتى تُشغّل وتُرفق أدلتها.

## 1. قواعد توثيق النتيجة

لكل حالة اختبار، سجّل:
- معرّف الاختبار والالتزام (commit SHA) وإصدار البناء.
- المنصة والجهاز وإصدار النظام، أو إصدار Godot وبيئة CI.
- خطوات إعادة الإنتاج والبيانات الابتدائية.
- المتوقع والفعلي، والنتيجة PASS/FAIL/BLOCKED/NOT RUN.
- السجلات ولقطات الشاشة/الفيديو ومقاييس الأداء عند الحاجة.
- رابط Issue أو Pull Request للإصلاح، ورقم إعادة الاختبار.

لا تُسجل PASS استنادًا إلى وجود الاختبار في المستودع أو نجاح مرحلة مختلفة من CI.

## 2. تصنيف الخطورة

| التصنيف | التعريف | مثال |
|---|---|---|
| Blocker / P0 | يمنع بدء اللعبة أو يسبب فقدان تقدم أو ثغرة حرجة | فساد حفظ مؤكد، انهيار عند بدء التشغيل |
| Critical / P1 | يكسر نظامًا أساسيًا أو يتيح استغلالًا جوهريًا | ضرر شبكي غير مصرح، تعطل القتال |
| Major / P2 | خلل كبير مع مسار بديل | تعطل مهمة أو جرد |
| Minor / P3 | أثر محدود بصري أو نصي | تداخل نص صغير |
| Performance / P* | تجاوز ميزانية الأداء المتفق عليها | هبوط FPS أو ارتفاع ذاكرة مستمر |

## 3. مصفوفة الأنظمة والاختبارات

| المجال | حالات الاختبار الأساسية | نوع الاختبار | دليل القبول |
|---|---|---|---|
| الإقلاع والموارد | تشغيل بارد، موارد ناقصة، مسارات مشاهد/عقد غير صالحة | Smoke / Static | لا أخطاء موارد أو انهيار |
| الحركة | مشي/ركض/قفز، تغيير اتجاه، مدخلات متزامنة، إيقاف الإدخال | Functional / Boundary | لا حركة عالقة ولا قيم غير محدودة |
| الاصطدام والعالم | جدار وزاوية ومنحدر وحافة وفتحة ضيقة، تصادم سريع | Integration / Physics | لا اختراقات أو سقوط خارج حدود العالم |
| الكاميرا | دوران سريع، حدود عمودية، تصادم كاميرا، تغيير دقة | Functional / UX | لا اهتزاز دائم أو انعكاس غير مقصود |
| القتال | إصابة/إخفاق، مسافة خارج النطاق، تكرار الهجوم، موت اللاعب/العدو | Unit / Integration | الضرر ضمن الحدود ومصدر الحقيقة موحد |
| الإحصاءات | صحة 0 وmax، ضرر 0 وسالب وكبير، خبرة عند حد المستوى | Boundary / Property | لا NaN/Inf ولا قيم خارج المجال |
| الأعداء والذكاء | اكتشاف وفقد الهدف، انتقال الحالات، حشود أعداء، إعادة ظهور | State / Stress | لا حالة عالقة أو نمو موارد غير محدود |
| المهمات والمكافآت | بدء/إنهاء/إعادة تحميل، قتل متكرر، منح المكافأة مرتين | Regression | تقدم ومكافآت idempotent |
| الجرد والعناصر | جرد فارغ وممتلئ، تكديس، استخدام عنصر، عنصر غير معروف | Unit / Boundary | لا فقد أو تكرار عناصر غير مبرر |
| الحوار وNPC | فتح/تقدم/إغلاق، تخطي الكتابة، اختيارات، قبول مهمة | Functional / UX | لا تجميد ولا تداخل واجهات |
| الحفظ | كتابة/قراءة، JSON تالف، نسخة قديمة، حقل ناقص أو خاطئ، انقطاع | Fault Injection / Recovery | استعادة سليمة أو رفض آمن دون فقد غير متوقع |
| الشبكة | هوية النظير، RPC غير صالح، رسائل متكررة، قطع وإعادة اتصال | Security / Integration | رفض الإدخال غير المصرح وعدم انهيار الخادم |
| المحتوى الخارجي | توقيع خاطئ، hash خاطئ، URL غير صالح، ZIP traversal، ملف كبير | Security / Boundary | رفض آمن دون كتابة خارج المسار |
| الصوت والمرئيات | ملفات مفقودة، مستويات الصوت، مزامنة مؤثرات، ترخيص الأصول | Content QA | لا أصول بلا مصدر/ترخيص |
| واجهة المستخدم | دقات مختلفة، أبعاد ونسب شاشة، لمس، لوحة مفاتيح، وضوح النص | UX / Compatibility | لا عناصر غير قابلة للوصول |
| الأداء | مشهد مزدحم، لعب 30–60 دقيقة، تبديل مشاهد، تحميل أصول | Profiling / Soak | لا نمو ذاكرة مستمر أو تجمد |
| Android | تثبيت/تشغيل/خلفية/استئناف/اتصال، مساحة منخفضة | Device Acceptance | اجتياز الخطوات على جهاز فعلي موثق |
| Web | Chrome/Firefox/Safari المستهدفة، HTTPS، تغيير حجم النافذة | Compatibility | لا أخطاء console حرجة |
| البناء والإصدار | إعادة بناء نظيفة، بصمة artifact، توقيع إنتاجي منفصل | Release / Supply chain | artifacts قابلة للتتبع بلا أسرار مضمّنة |

## 4. اختبارات حفظ عالية الأولوية

| ID | السيناريو | المتوقع |
|---|---|---|
| SAVE-001 | حفظ حالة سليمة ثم تحميلها | استعادة القيم المدعومة بدقة |
| SAVE-002 | JSON مقطوع أو مشوه | رفض آمن، عدم تطبيق حالة جزئية |
| SAVE-003 | صحة سالبة أو أكبر من الحد | رفض الحقل أو تطبيعه وفق سياسة موثقة |
| SAVE-004 | إحداثيات NaN/Inf أو خارج حدود العالم | عدم تمرير قيم غير finite أو خارج النطاق إلى الحركة |
| SAVE-005 | انقطاع العملية أثناء الكتابة | بقاء ملف سابق صالح أو استعادة نسخة احتياطية |
| SAVE-006 | فشل فتح/كتابة/استبدال الملف | إرجاع فشل صريح وتسجيل خطأ قابل للتشخيص |
| SAVE-007 | حقل جديد أو schema قديم | ترحيل محدد أو رفض متوافق موثق |
| SAVE-008 | تشغيل الاختبار مع وجود حفظ حقيقي | إعادة الملف الأصلي وعدم فقد بيانات المستخدم |
| SAVE-009 | إعادة تحميل مهمة مكتملة | عدم تكرار المكافأة |
| SAVE-010 | حفظ/تحميل Android بعد force-stop | استعادة متوقعة على جهاز فعلي |

## 5. اختبارات الحركة والفيزياء

1. اختبر جميع اتجاهات الحركة منفردة ومتزامنة، مع بدء/إيقاف سريع.
2. اختبر الجدران والزوايا والمنحدرات والحواف والفتحات الضيقة بسرعات مختلفة.
3. اختبر القفز قرب حافة، والهبوط على أسطح غير مستوية، والاصطدام أثناء الهجوم.
4. اختبر تكرار فتح/إغلاق الحوار والجرد أثناء الحركة؛ يجب أن تُطبق سياسة تجميد الحركة بصورة ثابتة.
5. نفّذ مسار لعب متكرر لمدة 15 دقيقة، وسجّل FPS والذاكرة والأخطاء.
6. كرر المسار على الجهاز المستهدف؛ الاختبار headless لا يثبت سلوك الإدخال والرسوميات الفعلية.

## 6. اختبارات الأداء والذاكرة

- عيّن أهداف الأداء حسب الأجهزة المستهدفة قبل الحكم: FPS، زمن الإطار p95، الذاكرة القصوى، زمن الإقلاع، وحجم التنزيل.
- سجّل baseline في مشهد هادئ ومشهد قتال ومشهد انتقال.
- كرر تحميل/تفريغ المشاهد 50 مرة، ثم قارن الذاكرة بعد الاستقرار؛ لا تعتبر زيادة مؤقتة وحدها تسربًا.
- اختبر 30 دقيقة على الأقل للـ soak الأولي، ثم اختبار أطول قبل الإصدار.
- احتفظ بسجل profiler وبيانات الجهاز والـ commit. لا تستخدم أرقامًا تقديرية على أنها قياسات فعلية.

## 7. بوابات قبول الإصدار

- [ ] Validate وBuild ناجحان على commit المرشح.
- [ ] لا توجد أخطاء Blocker أو Critical مفتوحة.
- [ ] الحفظ والاسترجاع واختبارات فساد الملف ناجحة.
- [ ] اختبارات الحركة والقتال والمهمات والجرد والحوار ناجحة.
- [ ] اختبار Android فعلي موثق، بما فيه الخلفية والاستئناف والحفظ.
- [ ] اختبارات Web على المتصفحات المستهدفة ناجحة.
- [ ] الشبكة مختبرة على جهازين قبل أي إعلان دعم لعب جماعي عام.
- [ ] كل أصل موزع له مصدر ورخصة وإسناد حيث يلزم.
- [ ] مفاتيح الإصدار والأسرار غير مضمنة في المستودع أو APK.
- [ ] حجم البناء والأداء والذاكرة ضمن أهداف مقاسة ومعلنة.
- [ ] تحديث سجل النتائج وحالة المشروع بعد كل تشغيل فعلي.

## 8. أوامر التحقق الآلي الحالية

تُشغّل من جذر المشروع بعد تثبيت Godot CLI 4.6 وPython 3، مع مراجعة كل exit code:

```bash
python3 tools/validate_docs.py
godot --headless --path . --editor --quit
godot --headless --path . --script res://tests/script_load_smoke_test.gd
godot --headless --path . --script res://tests/gameplay_smoke_test.gd
godot --headless --path . --script res://tests/gameplay_regression_test.gd
godot --headless --path . --script res://tests/player_character_smoke_test.gd
timeout 45s godot --headless --path . res://tests/network_combat_smoke_test.tscn
bash tools/test-network-loopback.sh
godot --headless --path . --script res://tests/content_catalog_smoke_test.gd
python -m unittest tools.test_package_content tools.test_sign_content_catalog -v
python -m unittest discover -s tools -p 'test_ai_test_diagnostics.py' -v
python3 -m py_compile tools/generate_player_glb.py tools/validate_free_assets.py
python3 tools/validate_free_assets.py
```

هذه أوامر اختبار موجودة أو موثقة في المشروع؛ لا تشغّلها على بيئة تحتوي بيانات حفظ مهمة دون مراجعة آلية استعادة ملف الحفظ. لا تستبدل هذه الأوامر اختبارات الجهاز الفعلي.

## 9. دورة التحقيق في العيوب

1. إعادة إنتاج العطل على commit محدد.
2. جمع سجل Godot وسجل النظام وخطوات التشغيل.
3. تصنيف الخطورة والنطاق والمنصة المتأثرة.
4. إنشاء اختبار regression يفشل قبل الإصلاح.
5. تنفيذ أصغر إصلاح آمن ممكن.
6. تشغيل الاختبار المستهدف ثم مجموعة CI كاملة.
7. اختبار المنصة الفعلية إذا كان العطل متعلقًا بالأداء أو الإدخال أو النظام.
8. إرفاق الدليل وتحديث التقرير، ثم إغلاق Issue بعد التحقق فقط.
