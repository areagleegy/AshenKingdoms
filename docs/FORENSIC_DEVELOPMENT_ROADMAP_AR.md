# خريطة التطوير والتحسين والتحقيق الجنائي — ممالك الرماد

> تاريخ الإعداد: 2026-10-21  
> النطاق: مراجعة ساكنة لمستودع GitHub وملفات محددة. ليست اختبار اختراق، ولا تشغيلًا محليًا للمشروع، ولا إثباتًا بأن CI ناجح. يجب ربط كل نتيجة تشغيلية بالـ commit والـ workflow الفعليين.

## 1. الملخص التنفيذي

المشروع يحتوي بالفعل على بنية لعب فردي، وحفظ محلي، ومهمة وحوار، وساحة لعب جماعي تجريبية عبر ENet، واختبارات Godot/Python في GitHub Actions. لا ينبغي إعادة بناء هذه الأنظمة من الصفر قبل قياسها. أكبر الأولويات هي سلامة الحفظ، والتحقق من مدخلات الشبكة، واختبارات الاسترجاع ومكافحة التكرار، وأمن إضافات المحرر وأدوات المحتوى، ثم إثبات قبول Android/Web على الأجهزة الفعلية.

### مستويات الدليل

- **مؤكد ساكنًا:** ما يمكن رؤيته مباشرة في ملف أو إعداد تمت قراءته.
- **مخاطرة محتملة:** مسار يستحق الاختبار، لكنه لا يثبت استغلالًا أو عطلًا فعليًا.
- **غير متحقق:** يحتاج تشغيلًا أو سجل CI أو جهازًا فعليًا.
- **لا يُدّعى:** لا يوجد هنا إثبات لاختراق فعلي أو اختبار ضغط أو قبول جهاز.

## 3. خطة العمل المرتبة

### المرحلة A — وقف المخاطر الحرجة (P0)

1. **الحفظ المحلي**
   - مراجعة PR #54 واختبار الكتابة والقراءة والحذف.
   - إضافة إصدار مخطط للحفظ، والتحقق من الأنواع والحقول والمدى الرقمي، وخطة ترحيل عند تغير البنية.
   - اختبار: JSON غير صالح، جذر ليس Dictionary، ملف مفقود، backup موجود، temp متروك، فشل rename/فتح ملف، حذف جزئي.
   - معيار القبول: لا يُفقد الحفظ السابق إذا فشل إنشاء الحفظ الجديد؛ لا يُقبل save غير مطابق للمخطط دون قرار واضح.

2. **سلامة RPC ومدخلات الحركة**
   - حصر كل الدوال الموسومة `@rpc` في المشروع.
   - التحقق من sender والعضوية والجلسة وحالة اللاعب ونوع القيم ومداها.
   - رفض Vector3 الذي يحتوي عناصر غير منتهية أو مكونات خارج حد متفق عليه قبل استخدامه في الفيزياء.
   - وضع حد معدل لكل peer ولكل فئة RPC، مع فصل الرسائل الموثوقة عن غير الموثوقة.
   - اختبار spam وNaN وInf والمتجهات الضخمة ورسائل من peer غير مالك وانقطاع الإدخال وإعادة الظهور.
   - لا يُعتبر وجود تحقق للمرسل في RPC واحدة دليلًا على أن كل RPC محمية.

3. **المكافآت والمهام**
   - اختبار إكمال المهمة ثم الحفظ والتحميل والتأكد من عدم تكرار المكافأة.
   - تخزين حالة منح المكافأة ضمن الحالة الدائمة نفسها، وجعل عملية منح المكافأة idempotent.
   - توحيد سلوك المهمة بين اللعب الفردي والشبكة أو توثيق الفرق صراحة.

4. **سلسلة التوريد وGitHub Actions**
   - مراجعة جميع `.github/workflows/*.yml`، والـ permissions، وsecrets، والـ artifacts، وأحداث pull_request.
   - عدم تمرير أسرار إلى تشغيل كود غير موثوق من مساهم خارجي.
   - تثبيت Actions على SHA كامل موثوق أو اعتماد lockfile مدعوم، مع مراجعة التحديثات.
   - فحص تبعيات Python وملفات القفل والتراخيص وعدم تنزيل محتوى غير ثابت أثناء الاختبارات.

### المرحلة B — اختبارات وأدوات تحقق قابلة للتكرار

1. الاستمرار في اختبارات Godot الحالية قبل إضافة إطار جديد.
2. تقييم **GdUnit4 6.2.x** المتوافق مع Godot 4.6 إذا احتجنا اختبارات مشاهد/Mocks/Fuzzing/تقارير JUnit؛ لا نثبت إصدارًا أحدث مخصصًا لـ Godot 4.7 دون اختبار توافق.
3. بديل أخف لاختبارات GDScript هو **GUT 9.6.1** المخصص لـ Godot 4.6؛ لا نضيف إطارين متداخلين إلا إذا ظهرت حاجة واضحة.
4. إضافة lint/format لـ GDScript، وفحوص Python (`unittest`, `py_compile`) وفحص روابط التوثيق والأصول.
5. حفظ تقارير الاختبار كـ artifacts مرتبطة بـ commit SHA، مع فصل نجاح التحليل عن نجاح الاختبارات وعن قبول الجهاز.
6. لا تُستخدم أدوات ذكاء اصطناعي لتعديل الملفات أو تنزيل أصول أو إرسال بيانات خارجية دون مراجعة صريحة؛ أي endpoint اختياري يجب أن يبقى معطلًا افتراضيًا وألا يطبع الأسرار.

### المرحلة C — قبول المنصات والأداء

- Android: بناء APK، تثبيته وتشغيله على جهاز فعلي، اختبار اللمس والواجهة العربية والصوت والذاكرة والحرارة والتحميل.
- Web: نشر عبر HTTP/HTTPS واختبار المتصفحات المستهدفة، الأحجام المختلفة، تحميل الموارد، الصوت، وحدود Web export.
- الشبكة: اختبار عميلين على جهازين وشبكة فعلية؛ قياس الانقطاع وفقد الحزم والتأخير. لا يُعلن Web multiplayer حتى وجود ناقل متوافق واختبار متكرر.
- الأداء: خط أساس ثابت للمشهد والكاميرا والدقة والإعدادات؛ تسجيل FPS/frame time والذاكرة ووقت التحميل وحجم APK وcommit والجهاز. الهدف المقترح 30 FPS ثابتة على جهاز مرجعي متفق عليه، لا ادعاء قياس غير منفذ.

### المرحلة D — تحسين جودة اللعبة

- البيئة: بناء منطقة قابلة للعب ذات مدخل وساحة قتال ومعلم بصري ومخرج، مع تصادم ومواد وإضاءة محسّنة.
- الشخصية والعدو: أصول GLB مرخصة، Rig/animations، وفصل hitbox عن mesh البصري.
- الصوت: مجموعة صغيرة متكاملة أولًا (خطوات، ضربة، إصابة، موت عدو، واجهة، مهمة) ثم الموسيقى.
- الواجهة: RTL، أحجام لمس مناسبة، أيقونات متناسقة، feedback واضح للهجوم والضرر والمهمة.
- كل أصل خارجي يحتاج مصدرًا وترخيصًا وإسنادًا وhash وسجل manifest؛ لا يُعتبر الرسم التجريبي دليلًا على اكتمال أصل داخل اللعبة.

### المرحلة E — إطلاق منضبط

لا يتم إصدار عام قبل:
- نجاح كل فحوص CI على commit المرشح.
- إغلاق أو قبول موثق لكل P0.
- إثبات قبول Android/Web فعليًا.
- مراجعة الأصول والتراخيص.
- تحديد توقيع Android وقناة التوزيع وسياسة التحديث.
- توثيق حدود اللعب الجماعي، ومراقبة الخادم، وخطة الاستجابة للحوادث.
- قرار إطلاق صريح مرتبط بالأدلة.

## 5. بروتوكول التحقيق الجنائي البرمجي

لكل نتيجة:
1. تثبيت commit SHA والفرع والملف/الدالة.
2. حفظ الحالة قبل التعديل وعدم الكتابة فوق دليل المصدر.
3. صياغة فرضية قابلة للدحض، لا وصفًا عامًا.
4. إنشاء اختبار يفشل قبل الإصلاح ويجتاز بعده.
5. تسجيل الأوامر، والبيئة، والنتيجة، والسجل، والـ artifact.
6. تصنيف النتيجة: Confirmed / Needs reproduction / Informational.
7. إنشاء PR مستقل وربطه بالقضية الأصلية.
8. إعادة الاختبار على commit الإصلاح.
9. لا تُرفع ملفات حفظ المستخدم أو الأسرار أو سجلات حساسة إلى artifacts.
10. لا يُعلن “تم الإصلاح” إلا بعد دليل تحقق مناسب؛ التوثيق أو قراءة الكود وحدها لا تثبت النجاح التشغيلي.

## 6. ما لم يتم التحقق منه في هذه المراجعة

- لم يتم تشغيل Godot أو أي اختبار على جهاز محلي في هذه المراجعة.
- لم يُنفذ اختبار اختراق أو ضغط أو استغلال فعلي.
- لم تُراجع كل ملفات المشروع أو كل نقاط RPC حتى الآن.
- لم تُفحص كل نتائج GitHub Actions على commit حديث.
- لم يتم اعتماد أو دمج PR #54.
- لم يتم تثبيت إضافة جديدة؛ المقترحات أعلاه تحتاج تجربة توافق وموافقة على التبعيات.

**الخطوة التالية الموصى بها:** إكمال PR #54 واختبارات الحفظ، ثم إغلاق متطلبات القضية #34 المتعلقة بالتحقق من مدخلات الشبكة ومكافآت المهام، مع عدم فتح الاستضافة العامة للإنتاج قبل استيفاء بوابات الأمان.
