# سجل توحيد أجزاء العصف الذهني — AshenKingdoms

- **الإصدار:** 1.0
- **تاريخ إعداد السجل:** 2026-10-24
- **الحالة:** مراجعة تحريرية/تنظيمية أولية؛ لا تعني اعتماد التنفيذ أو نجاح الاختبارات
- **النطاق:** أجزاء Part 14–18 والنصوص الأمنية والتدقيقية التي زُوّدت في سياق المشروع
- **القاعدة:** هذا السجل يوفّق بين النصوص المقدمة فقط؛ لا يدّعي أنه جرد كامل لكل صفحات ملف PDF أو لكل ملفات الأرشيف.

## 1. الغرض

تحتوي مواد العصف الذهني على تكرار في أرقام الأجزاء وعناوينها، وعلى مواصفات متقاربة لكنها ليست متطابقة. يحدد هذا السجل مرجعًا تنظيميًا مقترحًا، ويحفظ اختلافات النسخ دون اعتبار إحداها تنفيذًا فعليًا. لا ينبغي حذف النسخ التاريخية أو إعادة تسميتها بصمت.

## 2. قواعد فضّ التعارض

عند اختلاف النصوص:

1. **الكود والاختبارات ونتائج CI الحديثة** هي أدلة التنفيذ، وليست المواصفات وحدها.
2. **نطاق الإصدار وقرارات ADR المعتمدة** يحددان ما وافق عليه المشروع.
3. **وثائق السياسات** تحدد العملية المطلوبة، لكنها لا تثبت تطبيقها.
4. **النصوص المتكررة في العصف الذهني** تعامل كمقترحات تاريخية إلى أن تتم مراجعتها وربطها بمصدر رسمي.
5. أي بند لا يملك مالكًا ومعيار قبول ودليل تحقق يبقى مفتوحًا، ولا يوصف بأنه مكتمل.

## 4. أسماء مرجعية مقترحة

الأسماء التالية توصيات تنظيمية، وليست إعلانًا عن إنشاء الملفات:

- `docs/security/SECURITY_PROGRAM_OPERATIONS.md` — التشغيل الأمني ودورة الحياة والاستثناءات.
- `docs/KNOWLEDGE_MANAGEMENT.md` — إدارة المعرفة والذاكرة المؤسسية.
- `docs/RISK_MANAGEMENT.md` مع سجل فعلي في `docs/RISK_REGISTER.md`.
- `docs/audit/AUDIT_FRAMEWORK.md` — إطار التدقيق ودورة النتائج.
- `reports/FINDINGS_REGISTER.md` — سجل النتائج، مع تجنب إنشاء نسخ متنافسة في مسارات مختلفة.
- `docs/security/SECURITY_TESTING_PROGRAM.md` — استراتيجية الاختبارات الأمنية.
- `docs/REQUIREMENTS_MANAGEMENT.md` — إدارة المتطلبات والنطاق.
- `docs/archive/Part18_First_Playable_Slice_v07.md` — النسخة التاريخية من خطة الشريحة القابلة للعب، إذا لم يكن الملف موجودًا بالفعل.

قبل اعتماد أي مسار جديد، افحص الملفات الحالية والروابط والإشارات داخل CI. إذا كان هناك ملف مكافئ، فالأفضل توحيد محتواه وتحديث الروابط بدل إنشاء مرجع منافس.

## 5. نقاط تعارض يجب حسمها

### 5.1 مواقع السجلات

تستخدم النصوص أسماء ومسارات متباينة مثل `docs/RISK_REGISTER.md` و`RISK_REGISTER.md`، وكذلك `reports/FINDINGS_REGISTER.md` و`FINDINGS_REGISTER.md`. يجب تحديد مسار أساسي واحد لكل سجل، وإضافة روابط إحالة من الوثائق الأخرى بدل نسخ البيانات.

### 5.2 حالات النتيجة

يجب عدم خلط حالة الخطر بحالة النتيجة أو حالة الاختبار. الحد الأدنى المقترح:

- **Finding:** Open → Assigned → In Progress → Awaiting Verification → Closed أو Deferred.
- **Risk:** Open → Mitigating → Accepted/Monitored → Retired.
- **Test run:** Not Run → Pass أو Fail، مع حالات منفصلة للتخطي أو تعذر التشغيل عند الحاجة.
- **Requirement:** Proposed → Approved → Planned → Implemented → Verified → Retired.

لا يجوز اعتبار `Not Run` نجاحًا، ولا اعتبار `Deferred` إغلاقًا.

### 5.3 درجات المخاطر

النموذج المقترح `Risk Score = Likelihood × Impact` يعطي قيمة من 1 إلى 25 إذا استخدم مقياس 1–5 لكليهما. يجب توثيق الحدود والتصرف المطلوب، وعدم استخدام كلمة «حرج» دون تعريف. يلزم أيضًا توثيق المخاطر المقبولة ومالكها وتاريخ مراجعتها.

### 5.4 معايير الإغلاق

إغلاق نتيجة تدقيق يتطلب على الأقل: تغييرًا محددًا، واختبارًا مناسبًا ناجحًا، ودليلًا مرتبطًا بالـ commit، ومراجعة مستقلة عند الحاجة، وتحديث السجل. إغلاق النتيجة لا يثبت أن جميع المخاطر المرتبطة بالنظام زالت.

### 5.5 ادعاءات الشريحة القابلة للعب

تسلسل الحركة والحوار والمهمة وقتل ثلاثة أعداء والمكافأة والحفظ وإعادة التحميل معيار قبول مفيد، لكنه ليس دليلًا على نجاحه. يلزم تقرير تشغيل، وإصدار APK/commit محدد، وطراز جهاز وإصدار Android، ونتيجة لكل خطوة، وسجل الأعطال، وقياس أداء قابل للتكرار. لا يُعلن اكتمال الشريحة اعتمادًا على الخطة وحدها.

## 6. نموذج تتبع موحد

لكل متطلب أو نتيجة، سجّل الحقول المناسبة من الآتي:

- المعرف والعنوان والفئة.
- المصدر والرابط إلى Part أو ADR أو Issue/PR.
- المالك والمراجع.
- الحالة والأولوية والتاريخ.
- الملفات أو الأنظمة المتأثرة.
- معيار القبول وطريقة التحقق.
- رابط الاختبار وسجل التشغيل والـ commit SHA.
- المخاطر المتبقية والاستثناء وتاريخ انتهائه، إن وجد.
- قرار الإغلاق واسم المراجع ودليل الإغلاق.

لا تُدخل أسرارًا أو مفاتيح توقيع أو بيانات اعتماد في السجلات أو مرفقات CI.

## 7. خطة الاستكمال بالترتيب

1. **جرد:** فحص شجرة المستودع بحثًا عن ملفات Part 14–18 والسجلات المشار إليها، ثم تسجيل الموجود والمفقود والمكرر.
2. **مطابقة:** ربط كل بند من النصوص بملف مصدر أو Issue أو اختبار أو تصنيفه كمقترح غير متحقق.
3. **توحيد:** اختيار مرجع أساسي واحد لكل موضوع وتسجيل النسخ المتعارضة في سجل التغييرات.
4. **تحقق الروابط:** تشغيل مدقق الوثائق، وإصلاح الروابط والمسارات المعطوبة دون حذف الملفات التاريخية.
5. **تحقق التنفيذ:** تشغيل الاختبارات المناسبة على commit محدد، وحفظ النتائج الفعلية لا النتائج المتوقعة.
6. **مراجعة مستقلة:** مراجعة التغييرات التي تمس الأمن أو المعمارية أو الإصدارات قبل الدمج.
7. **تحديث الحالة:** تحديث فهرس الوثائق وسجل العمل والحالة بعد توفر الأدلة فقط.
