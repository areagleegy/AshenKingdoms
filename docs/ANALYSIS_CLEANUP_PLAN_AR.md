- **النطاق:** تجميع الأفكار والمواصفات المقدمة في المحادثة مع فحص مرجعي لملفات المستودع والوثائق الرسمية

## 1. الغرض وحدود الاستنتاج

تهدف هذه الوثيقة إلى تنظيف وتوحيد العصف الذهني وتحويله إلى خطة قابلة للتنفيذ والتتبع. وهي لا تدّعي أن كل ملفات PDF أو كل سجل المحادثات قد تمت قراءته كاملًا في هذه المراجعة، ولا أن كل اختبار أو إصلاح قد نُفذ. تمت مراجعة README وفهرس الوثائق وحالة التنفيذ ودليل التوثيق المتاحة عبر GitHub، إضافة إلى مقتطفات المادة المرفوعة ومرجعيات Godot الرسمية.

**قاعدة الأدلة:** الخطة ليست تنفيذًا، ووجود الكود ليس إثباتًا لصحته، ونجاح CI لا يثبت وحده صلاحية اللعب على جهاز فعلي أو جاهزية الأمن للإنتاج.

## 2. مصادر الحقيقة وترتيب الأولوية

عند التعارض، يُتبع هذا الترتيب للتحقق من الحالة الراهنة:

1. الشيفرة والمشاهد وموارد Godot الفعلية.
2. ملفات سير العمل ونتائج CI المرتبطة بالـ commit نفسه.
3. الاختبارات الآلية وتقارير الاختبار اليدوي وأدلة الأجهزة.
4. وثائق الحالة والنطاق المعتمد والبنية التقنية.
5. ADRs والسياسات والخطط المؤرشفة.
6. المحادثات والعصف الذهني والمقترحات غير المتحقق منها.

يجب تسجيل أي تعارض بين الكود والوثائق كفجوة، ثم إما تعديل التنفيذ أو تصحيح الوثيقة في تغيير صغير قابل للمراجعة. لا تُغيّر الوثائق المعتمدة أو المؤرشفة بصمت.

## 3. خلاصة الحالة المرصودة من README

يصف README المشروع بأنه نموذج أولي قيد التطوير مبني على Godot 4.6 وGDScript. ويذكر وجود حلقة لعب فردي وحوار ومهمة تجريبية وحفظ محلي وحزم محتوى اختيارية وساحة شبكة ENet تجريبية، مع توضيح أن ذلك لا يعني اكتمال اللعب الجماعي أو النشر الإنتاجي.

القيود المهمة المعلنة في README:

- اللعب الجماعي عبر Web غير مدعوم حاليًا.
- ساحة ENet تجريبية وليست نظامًا إنتاجيًا آمنًا.
- لا توجد مصادقة حسابات إنتاجية أو خدمة استضافة عامة مُدارة أو حفظ شبكي دائم مثبت.
- الحزم الاختيارية لا تملك CDN أو فهرسًا إنتاجيًا منشورًا أو مفتاح توقيع إنتاجيًا مضبوطًا؛ التنزيل معطل افتراضيًا.
- ملف APK الناتج من CI تجريبي وغير موقع كمخرج إنتاجي، ويجب تثبيته واختباره على هاتف فعلي.
- نجاح الاختبارات المحلية أو CI يخص الفحوص التي شُغّلت فقط.

المرجع: [README.md](../README.md)، [حالة التنفيذ](PROJECT_STATUS_AR.md)، [نطاق الإصدار](RELEASE_SCOPE_AR.md).

## 4. التنظيف البنيوي للأجزاء والوثائق

### 4.1 قاعدة منع التكرار

توجد في العصف الذهني نسخ متداخلة من أجزاء إدارة المخاطر والتدقيق والعمليات الأمنية. يجب عدم الاحتفاظ بنسخ متنافسة تحمل رقم Part واحدًا دون بيان العلاقة بينها.

- لكل موضوع وثيقة مرجعية نشطة واحدة.
- تحفظ النسخ السابقة في الأرشيف مع تاريخها وسبب استبدالها.
- تضاف في بداية النسخة المؤرشفة ملاحظة أنها مرجع تاريخي وليست سياسة تشغيلية نافذة إذا استُبدلت.
- لا يُعاد ترقيم الأجزاء القديمة تلقائيًا؛ يُنشأ جدول ربط بين رقم الجزء في المحادثة والمسار المرجعي الحالي.
- عند وجود اختلاف بين Part 14 أو 15 أو 16 أو 17 أو 18، تُسجل الفروق كقرارات تحريرية ولا تُدمج البنود المتعارضة دون قرار صريح.

### 4.2 خريطة المواضيع

| الموضوع | المخرج المرجعي المقترح | معيار الاكتمال |
|---|---|---|
| الحوكمة والأمن التشغيلي | وثيقة أمن تشغيلية واحدة + سجل الاستثناءات | مالك ومراجع وتاريخ مراجعة لكل ضابط |
| التدقيق والنتائج | سجل Findings وتقارير التدقيق | كل Finding لها شدة ومالك ودليل وحالة |
| الاختبارات الأمنية | اختبارات قابلة للتشغيل داخل tests/ | نتيجة آلية قابلة للتكرار ودليل مرتبط بالـ commit |
| المخاطر | سجل مخاطر مركزي | احتمال وأثر ومالك وخطة معالجة وتاريخ مراجعة |
| إدارة التغيير | قالب Change Request وADR عند الحاجة | أثر ونطاق ومخاطر وخطة رجوع ومعايير قبول |
| المتطلبات والنطاق | متطلبات قابلة للتتبع | هدف ومالك وقبول واختبار وميلستون |
| النسخة القابلة للعب | نطاق Vertical Slice واحد | حركة وتفاعل ومهمة وقتال ومكافأة وحفظ واستعادة على جهاز فعلي |
| الأصول والتراخيص | سجل آلي للمصادر والرخص والبصمات | لا مورد مجهول المصدر أو الرخصة |

هذه خريطة تنظيمية وليست ادعاءً بأن كل الملفات المقترحة موجودة بالفعل.

## 5. أولويات التنفيذ

### P0 — تثبيت الحالة الأساسية

1. تأكيد رأس الفرع والـ commit الحالي ونتائج Actions وPRs المفتوحة.
2. تشغيل مدقق الوثائق واختبارات المشروع الحالية دون تغيير وظيفي واسع.
3. إنشاء جرد للملفات والمشاهد والسكربتات والإضافات ومخرجات البناء.
4. توثيق الأخطاء الفعلية مع سجل الأمر ورمز الخروج وcommit SHA.
5. الحفاظ على حدود PR #95 كما هو موثق في سجل الاستمرارية؛ لا تُوسّع نطاقه دون قرار مستقل.

### P1 — أمان الحفظ والشبكة

- مراجعة مسار الحفظ الحقيقي: حدود حجم الملف، المخطط والإصدار والأنواع والحقول المسموح بها، التعامل مع الملفات الفاسدة، والكتابة الذرية.
- لا تعتمد على التشفير وحده لمنع التلاعب؛ التحقق من المخطط وسلامة الملف لا يجعل بيانات العميل موثوقة في لعبة شبكية.
- في الشبكة، تعامل مع كل مدخل من العميل على أنه غير موثوق. يتحقق الخادم من الحركة والمدى والضرر والمخزون والمكافآت والتوقيت ومعدل الطلبات.
- اختبر إعادة إرسال الأوامر والتزامن والمكافآت المكررة وحدود RPC، ولا تدّعِ أن هذه الحماية موجودة حتى يثبت الكود والاختبار ذلك.
- لا تضع مفاتيح توقيع أو أسرار API داخل المستودع أو APK.

### P1 — النسخة القابلة للعب v0.7

النطاق المقترح هو حلقة صغيرة مكتملة: تشغيل، حركة، تفاعل مع NPC، قبول مهمة، هزيمة ثلاثة أعداء، استلام المكافأة، حفظ، خروج، إعادة تشغيل، واستعادة التقدم. يجب أن تنجح على جهاز Android فعلي ضمن قائمة الأجهزة المستهدفة.

لا يُوسع العالم أو تُضاف أنظمة ضخمة قبل إتمام هذه الحلقة. يُؤجل تعدد اللاعبين المتقدم وتنزيل المحتوى والإضافات الثقيلة إلى أن تُثبت الحاجة والميزانية.

### P2 — الذكاء الاصطناعي والملاحة

- ابدأ بمشهد اختبار صغير يحوي أرضية وNavigationRegion3D وNavigationAgent3D وعدوًا ولاعبًا ونقطة هدف.
- افصل اختبار تحميل السكربت عن اختبار سلوك الملاحة الفعلي.
- تحقق من انتقالات FSM، وتحديث الهدف، والوصول إلى المسار، وفقدان الهدف، وحدود الهجوم، ومنع الضرر غير المصرح به.
- لا تضف Terrain3D أو بث عالم واسع قبل قياس أثره على الأجهزة المستهدفة.

### P2 — الأصول والأداء

- كل أصل خارجي يجب أن يسجل المصدر والمؤلف والرخصة وحقوق الاستخدام التجاري والتعديل ومتطلبات الإسناد وبصمة SHA-256.
- افحص توافق الإضافات مع إصدار Godot الفعلي والمنصات المستهدفة قبل اعتمادها.
- قس حجم APK ووقت التحميل وFPS والذاكرة ووقت الإطار على أجهزة مرجعية.
- أهداف مثل 60 FPS على الحاسوب أو 30 FPS على Android هي أهداف قبول أولية فقط إلى أن تُوثق الأجهزة والإعدادات وطريقة القياس.

## 6. بوابات التحقق المطلوبة

لا يُغلق العمل إلا عند تحقق البوابة ذات الصلة:

1. **Parse / Import:** لا أخطاء تحليل أو موارد مفقودة في مسار الاختبار المحدد.
2. **Unit / Smoke:** نجاح الاختبارات المعنية مع رمز خروج صفر وسجل محفوظ.
3. **Integration:** اختبار التكامل بين الأنظمة، لا تحميل السكربت فقط.
4. **Security:** اختبارات سلبية وإيجابية تثبت رفض الحالات غير الصحيحة وقبول الحالات الصحيحة.
5. **Android:** تصدير ناجح، تثبيت، تشغيل، اختبار الحلقة الأساسية، وحفظ/استعادة على جهاز فعلي.
6. **Performance:** قياسات موثقة مع الجهاز والإعدادات ومدة الاختبار ونسخة البناء.
7. **Evidence:** ربط الدليل بالـ commit أو PR أو Action run.
8. **Review:** مراجعة مستقلة للتغييرات الحساسة، وتحديث الوثائق وسجلات المخاطر والنتائج.
9. **Closure:** تحقق معايير القبول وإضافة اختبار انحدار لأي عيب أمني مغلق.

## 7. نموذج سجل النتائج

استخدم الحقول التالية في السجل الرئيسي، مع ربط كل نتيجة بدليل محدد:

| الحقل | المعنى |
|---|---|
| ID | معرف ثابت لا يعاد استخدامه |
| Severity | Critical / High / Medium / Low |
| Category | Security / Gameplay / Build / Performance / Docs / License |
| Observation | ما شوهد بالفعل دون استنتاج غير مدعوم |
| Evidence | مسار اختبار أو رابط Action أو commit أو تقرير جهاز |
| Owner | مسؤول المعالجة |
| Status | Open / Assigned / In Progress / Awaiting Verification / Closed / Deferred |
| Acceptance | النتيجة التي تسمح بالإغلاق |
| Verification | من تحقق ومتى وبأي أمر |
| Regression Test | اختبار يمنع عودة العيب |
| Review Date | موعد المراجعة التالية |

لا تسجل نتيجة Pass أو Finding بلا فحص محدد. إذا تعذر الفحص، تسجل الحالة **Not Verified** مع السبب، ولا تحولها إلى Pass.

## 8. تصحيحات تقنية يجب مراعاتها أثناء مراجعة النصوص والكود

- لا تُستخدم نتائج اختبار smoke لتحميل السكربت كدليل على سلوك اللعبة الكامل.
- لا تُقبل أمثلة الشبكة التي تسمح للعميل بإرسال الحالة النهائية للاعب أو الضرر دون تحقق سلطوي من الخادم.
- لا تُعد كتابة ملف الحفظ مباشرةً إلى الملف النهائي كتابةً ذرية؛ يجب التحقق من استراتيجية الملف المؤقت والاستبدال والتعامل مع الفشل.
- لا يُعتبر checksum أو التشفير المحلي بديلًا عن التحقق من المدخلات أو سلطة الخادم.
- يجب التمييز بين APK تجريبي ونسخة Release موقعة بمفتاح محفوظ خارج المستودع.
- لا تُعتمد أرقام إصدارات SDK أو NDK المنسوخة من ملاحظات قديمة قبل مقارنتها بوثائق Godot 4.6 الحالية.
- لا يُفترض أن أي إضافة أو نموذج ثلاثي الأبعاد أو حزمة مجانية تسمح تلقائيًا بالاستخدام التجاري أو إعادة التوزيع.

## 11. معايير الاكتمال

تُعتبر عملية التنظيف مكتملة عندما:

- لكل موضوع وثيقة مرجعية واحدة ومسارات الروابط تعمل.
- الأجزاء المتكررة محفوظة تاريخيًا ومعلّمة بوضوح.
- كل ميزة موصوفة بحالتها: Implemented / Experimental / Planned / Deferred / Not Verified.
- كل نتيجة تدقيق لها دليل ومالك ومعيار إغلاق.
- كل تغيير أمني مغلق محمي باختبار انحدار.
- نسخة Android التجريبية مثبتة ومختبرة على جهاز فعلي قبل إعلان قبولها.
- المصادر والرخص موثقة لكل أصل خارجي.
- لا تُعرض الخطط أو نتائج الفحوص القديمة باعتبارها حالة حية مؤكدة.
