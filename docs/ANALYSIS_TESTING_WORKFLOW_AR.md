# منهجية التحليل والفحوصات والتحقيق — ممالك الرماد

- تاريخ المراجعة: 2026-10-23
- المستودع: https://github.com/areagleegy/AshenKingdoms
- الفرع المرجعي عند إعداد الوثيقة: \`main\`
- التقنية: Godot 4.6 / GDScript، Android ARM64 وWeb، وENet تجريبي
- النطاق: النموذج الأولي والإصدار التجريبي؛ هذه الوثيقة لا تعني أن كل الاختبارات أو مراحل القبول قد نُفذت.

## 1. المبادئ الحاكمة

1. **الدليل قبل الحكم:** لا تُسجل نتيجة PASS إلا بعد تشغيل الاختبار على commit معروف والتحقق من نتيجته.
2. **افصل الحقائق عن الفرضيات:** ميّز بين نتيجة كود/اختبار/CI، وملاحظة يدوية، وتوقع يحتاج تجربة.
3. **اختبر من الأقل تكلفة إلى الأعلى:** تحليل ساكن ووحدات، ثم تكامل، ثم تشغيل كامل، ثم جهاز فعلي/شبكة فعلية.
4. **اختبر العطل قبل الإصلاح وبعده:** أنشئ حالة إعادة إنتاج واختبار انحدار، ثم شغّل الاختبار المستهدف ومجموعة التحقق ذات الصلة.
5. **اجعل AI مساعدًا لا مصدر حقيقة:** يمكنه تجميع السجلات وتصنيفها واقتراح فرضيات؛ لا يُسمح له بتأكيد النجاح بلا دليل أو تعديل حالة اللعبة/قاعدة البيانات من تلقاء نفسه.
6. **حافظ على خصوصية اللاعب:** لا ترفع تلقائيًا نصوص الحوار الخاصة أو ملفات الحفظ أو عناوين IP أو مفاتيح API. اجمع الحد الأدنى اللازم، مع موافقة صريحة لأي خدمة خارجية.
7. **الإصدار التجريبي ليس إنتاجًا:** لا تُفعّل خادمًا عامًا أو حزم محتوى إنتاجية أو توقيع إصدار دائم لمجرد نجاح CI.

## 2. مراحل التحليل

### A. تثبيت خط الأساس

- سجّل SHA للفرع وطلبات السحب المفتوحة والـ workflows المرتبطة به.
- راجع \`README.md\` و\`docs/PROJECT_STATUS_AR.md\` و\`docs/TECHNICAL_ARCHITECTURE.md\` و\`docs/RELEASE_SCOPE_AR.md\`.
- حدد ما هو منفذ فعليًا وما هو تجريبي أو مؤجل، ثم اربط كل ادعاء بملف أو اختبار أو تشغيل CI.
- لا تخلط نجاح فرع PR بنجاح \`main\`، ولا تستخدم أرقام أداء أو أحجام من بناء قديم على أنها baseline حالي.

### B. المعمارية وتدفق البيانات

وثّق لكل نظام: نقطة الدخول، مالك الحالة، المدخلات، المخرجات، حدود الثقة، الأخطاء المتوقعة، وطريقة الاختبار.

| النظام | ما يجب تتبعه | حدود الثقة المهمة |
|---|---|---|
| اللعب الفردي | الإدخال ← اللاعب/الفيزياء ← القتال والصحة ← المهمة/الجرد ← الحفظ | بيانات الحفظ مدخل غير موثوق ويجب التحقق منها قبل تطبيقها |
| الحوار وNPC | التفاعل ← DialogueManager ← العقد والاختيارات ← أعلام المهمة والحفظ | نص الحوار لا ينبغي أن ينفذ كودًا أو يمنح مكافأة خارج قواعد اللعبة |
| ENet | العميل ← RPC ← تحقق الخادم ← الحالة authoritative ← مزامنة العملاء | لا تثق في الصحة أو الضرر أو المكافأة التي يرسلها العميل |
| حزم المحتوى | مصدر/URL ← فهرس موقع ← تنزيل ← hash وتوقيع ← staging ← تثبيت | لا تثبّت حزمة قبل التحقق من المصدر والمسار والحجم والتوقيع |
| Android/Web | إعدادات التصدير ← موارد البناء ← التشغيل ← الإدخال/الرسوميات/الصوت | نجاح التصدير لا يثبت تشغيلًا ناجحًا على جهاز/متصفح فعلي |
| أدوات AI | سجل منقح ← محلل محلي ← مخرجات تفسيرية ← مراجعة بشرية | مخرجات النموذج اقتراحات؛ لا تمنح صلاحيات ولا تنفذ إصلاحات تلقائية على main |

### C. المتطلبات الوظيفية وغير الوظيفية

لكل ميزة، أنشئ معرّف متطلب ومعايير قبول قابلة للملاحظة. لا تستخدم «يعمل جيدًا» كمعيار.

- **وظيفي:** الحركة، القفز، الاصطدام، الهجوم، الضرر والموت، الذكاء الاصطناعي للأعداء، الجرد، المهمات، الحوار والاختيارات، الحفظ والتحميل، اتصال الشبكة.
- **الأداء:** FPS، زمن الإطار p95، ذاكرة الذروة وبعد الاستقرار، زمن الإقلاع وتحميل المشاهد، حجم APK/Web.
- **الاستقرار:** لا انهيار أو تجمد أو نمو ذاكرة مستمر في جلسة طويلة، وتعافٍ متوقع بعد الخلفية/الاستئناف أو انقطاع الشبكة.
- **الأمان:** تحقق المدخلات، سلطة الخادم، حدود RPC، سلامة الحفظ، مصدر الأصول والرخص، وعدم تضمين الأسرار.
- **قابلية الاستخدام:** وضوح النص العربي، قابلية الوصول للأزرار على شاشات مختلفة، عمل اللمس والكاميرا، وإمكانية استعادة الخطأ برسالة مفهومة.
- **التوافق:** إصدار Android والجهاز والمعمارية، المتصفحات المستهدفة، دقة الشاشة ونسبة الأبعاد.

تُحدد حدود الأداء قبل قياس المرشح النهائي. لا تخترع ميزانية FPS أو ذاكرة دون تحديد الأجهزة المستهدفة والقياس الفعلي.

## 3. هرم الاختبارات

| الطبقة | الغرض | أمثلة للمشروع | بوابة الانتقال |
|---|---|---|---|
| 1. تحليل ساكن | كشف أخطاء الصياغة والموارد والمخالفات قبل التشغيل | استيراد Godot، تحميل GDScript والمشاهد، فحص الوثائق والأصول، اختبارات Python | لا أخطاء تحليل/موارد حرجة |
| 2. Unit / Logic | اختبار منطق صغير بحالات حدية | الصحة، الخبرة، اختيار الحوار، مكافأة المهمة مرة واحدة، التحقق من الحفظ | جميع الحالات المحددة ناجحة |
| 3. Integration | اختبار التفاعل بين الأنظمة | اللاعب والصحة والقتال، الحوار والمهمة والحفظ، فهرس المحتوى والمثبّت | التغييرات تنتقل بصورة صحيحة دون أثر جانبي |
| 4. System / Regression | اختبار حلقة لعب كاملة وإعادة تشغيل السيناريو | تشغيل المشهد، قتال، إكمال مهمة، حفظ ثم تحميل | لا أخطاء حرجة أو تراجع عن baseline |
| 5. UI/UX / Device | اختبار إدخال ورسوم وصوت على منصة فعلية | أزرار اللمس، تدوير الكاميرا، دورة التطبيق، مقاسات الشاشة | دليل جهاز/نظام موثق |
| 6. Performance / Soak | كشف تدهور الأداء والتسرب والتجميد | مشهد مزدحم، تبديل مشاهد، 30 دقيقة أو أكثر، قياس p95 والذاكرة | ضمن ميزانيات محددة مسبقًا |
| 7. Network / Security | اختبار حدود الثقة والأخطاء العدائية | عميلان، RPC غير صالح، تكرار رسائل، قطع اتصال، ضغط متدرج | لا سلطة عميل غير مصرح بها ولا انهيار |
| 8. UAT / Release | إثبات ملاءمة الإصدار التجريبي للغرض المعلن | قائمة قبول Android وWeb، الحفظ، القتال، الحوار، الأصول والتراخيص | قبول موثق أو رفض مع أسباب واضحة |

## 4. التحليل الساكن والأدوات

الأدوات الموجودة في المستودع والتي ينبغي إعادة التحقق من نتائجها لكل commit:

- \`godot --headless --path . --editor --quit\` لاستيراد المشروع وكشف مشكلات الموارد.
- \`tests/script_load_smoke_test.gd\` لتحميل السكربتات والمشاهد ومسارات العقد التي يغطيها الاختبار.
- \`tools/validate_docs.py\` للتحقق من روابط التوثيق المحلية.
- \`tools/validate_free_assets.py\` لفحص سجل الأصول ومتطلبات الترخيص التي تنفذها الأداة.
- اختبارات Python الحالية ضمن \`tools/test_*\` واختبارات GDScript المدرجة في [خطة الاختبار](TEST_PLAN.md).
- GitHub Actions في \`.github/workflows/validate.yml\` و\`.github/workflows/build.yml\`؛ يجب فحص الـ commit والنتيجة النهائية لكل Job.

**فجوات لا يجوز افتراض إغلاقها:** وجود workflow لا يثبت أن فحصًا أمنيًا شاملًا أو Linter متخصصًا لـ GDScript أو فحص dependency/SBOM قد أُضيف. قبل إضافة أداة جديدة، تحقّق من صيانتها، وترخيصها، ودعمها لـ Godot 4.6، ومعدل الإنذارات الكاذبة، وكلفة تشغيلها. أضفها تدريجيًا مع تثبيت الإصدار أو SHA وتوثيق سبب الاختيار.

## 5. مختبر السيناريوهات داخل اللعبة

لكل سيناريو سجل موحد يحوي \`scenario_id\`، المتطلبات السابقة، المدخلات، الخطوات، النتيجة المتوقعة، النتيجة الفعلية، مدة التنفيذ، وبيانات البيئة.

- **الحركة/الفيزياء:** المشي والركض والقفز، الاتجاه القطري، الجدران والزوايا والمنحدرات والحواف، إيقاف الإدخال، تكرار الضغطات.
- **القتال:** هجوم ضمن المدى وخارجه، cooldown، ضرر حدّي، الموت وإعادة الإحياء، العدو الميت، هجمات متزامنة وتكرار الطلب.
- **AI الأعداء:** اكتشاف الهدف وفقده، انتقال الحالات، التوقف عند الموت، عدد أعداء متزايد، وعدم بقاء AI في حالة غير نهائية.
- **الحوار:** فتح/إغلاق، تخطي الكتابة، اختيار صالح وغير صالح، أعلام الحوار، بدء المهمة، إعادة الحوار بعد التحميل.
- **المهمة والجرد:** مكافأة لمرة واحدة، قتل متكرر، حقيبة فارغة وممتلئة، تكديس واستخدام العناصر، حفظ/تحميل الحالة.
- **الحفظ:** JSON تالف، حقول مفقودة أو أنواع خاطئة، قيم غير finite، إحداثيات خارج العالم، انقطاع أثناء الكتابة، ملف قديم.
- **الشبكة:** client/server، هوية المرسل، معدل RPC، رسالة مكررة، قيم NaN/Inf، انقطاع وإعادة اتصال، عميلين على جهازين.
- **المحتوى والأصول:** توقيع/hash خاطئ، ZIP traversal، ملف كبير، ملف ناقص، ترخيص/إسناد مفقود، صوت أو نموذج غير قابل للتحميل.
- **المنصة:** تثبيت وتشغيل وخلفية واستئناف ودوران الشاشة والمساحة المنخفضة على Android؛ أخطاء console وتغيير الحجم وHTTPS في Web.

لا تدّعِ أن الاختبار الآلي غطّى سيناريوهات اللمس أو الفيزياء الكاملة إذا كان ينفذ منطقًا معزولًا فقط. علّم السيناريو غير المؤتمت \`BLOCKED\` أو \`NOT RUN\` بدل \`PASS\`.

## 6. دور الذكاء الاصطناعي في الاختبار والتحقيق

### مسار آمن ومجاني أولًا

1. اجمع الأحداث المنظمة من QA build، مع وقت نسبي ومعرّف السيناريو وقيم رقمية لازمة فقط.
2. حلل JSON محليًا بقواعد حتمية أولًا؛ يجب أن تنتج القواعد نفسها النتيجة نفسها لنفس المدخل.
3. اجمع مقاطع السجل ذات الصلة بعد إزالة الأسرار والبيانات الشخصية.
4. يمكن لنموذج محلي اختياري أن يلخص الأدلة ويقترح أسبابًا واختبارات إضافية. لا حاجة إلى مفتاح API أو خدمة مدفوعة لهذا المسار.
5. اطلب من المحلل إخراج: الأدلة، الفرضية، درجة الثقة مع سببها، خطوات إعادة الإنتاج، الاختبار المقترح، والبيانات الناقصة.
6. يراجع المطور الفرضية، وينشئ اختبار انحدار وإصلاحًا منفصلًا، ثم يشغّل CI.
7. لا يُسمح للـ AI بدمج PR، أو تغيير بيانات الإنتاج، أو تجاوز بوابات الإصدار، أو إرسال تقارير الجهاز إلى جهة خارجية دون موافقة صريحة.

### قواعد التقييم

- لا يعتبر النص المولّد دليلًا على أن العطل حدث.
- اربط كل استنتاج بمعرّفات أحداث/أسطر سجل قابلة للمراجعة.
- افصل \`observed\` عن \`inferred\` و\`unknown\`.
- إذا نقصت البيانات، أخرج \`insufficient_evidence\` بدل اختلاق سبب.
- اختبر محلل AI على حالات معروفة وإشارات كاذبة، وقِس precision/recall حيث توجد تسميات مرجعية.
- أبقِ تحليل القواعد متاحًا إذا تعطل النموذج أو لم يكن مثبتًا.

## 7. إدارة العيوب والأولويات

لكل عيب افتح Issue أو اربطه بواحد موجود، مع: العنوان، الأولوية، commit، المنصة، خطوات إعادة الإنتاج، المتوقع/الفعلي، دليل منقح، التكرار، الأثر، والاختبار الذي يمنع الرجوع.

- **P0 / Blocker:** فقدان بيانات أو تعطل بدء التشغيل أو استغلال جوهري.
- **P1 / Critical:** نظام أساسي مكسور أو تجاوز حدود الثقة.
- **P2 / Major:** ميزة أساسية مكسورة مع بديل محدود.
- **P3 / Minor:** أثر بصري/نصي محدود.
- **Performance:** تجاوز قياس متفق عليه أو تدهور مستمر.

دورة الإصلاح: إعادة إنتاج ← اختبار يفشل قبل الإصلاح ← أصغر تغيير ممكن ← اختبار مستهدف ← regression وCI ← اختبار الجهاز/الشبكة إذا لزم ← توثيق النتيجة. لا تدمج تغييرات متداخلة في الحفظ أو الشبكة أو المحتوى دون مراجعة الاعتماد بينها.

## 8. تقسيم المسؤوليات

يمكن تنفيذ الأدوار بواسطة شخص واحد أو وكلاء منفصلين؛ لا يعني هذا الجدول أن وكلاء أو أجهزة قد شُغّلت فعليًا.

| المسار | المسؤولية | مخرجات قابلة للمراجعة |
|---|---|---|
| قائد QA | تحديد نطاق المرشح وبوابات القبول وتجنب تضارب الفروع | خطة اختبار، سجل قرارات، ملخص قبول |
| محلل معماري | تتبع تدفق الحالة وحدود الثقة والاعتماديات | خريطة أنظمة، قائمة مخاطر مرتبطة بالملفات |
| مسؤول اختبارات المنطق | وحدات واختبارات regression | اختبارات قابلة للتشغيل وسجل نتائج |
| مسؤول أجهزة Android/Web | إدخال/واجهة/صوت/أداء ودورة التطبيق | سجل جهاز وفيديو/لقطات منقحة وقياسات |
| مسؤول الشبكة والأمان | RPC، سلطة الخادم، انقطاع الاتصال والضغط | سيناريوهات إساءة استخدام ونتائج جهازين |
| مسؤول الأصول | التحميل والحجم والرخص والإسناد | جرد أصول وبصمات ومصادر موثقة |
| مساعد AI | تلخيص أدلة منقحة واقتراح حالات اختبار | تقرير فرضيات قابل للتتبع، لا تغييرات تلقائية |
| مراجع الدمج | مراجعة diff والاختبارات والاعتماديات | قرار مراجعة ونتائج CI على رأس PR |

## 9. ترتيب التنفيذ المقترح

1. **Baseline:** تثبيت commit المرشح، حالة الفروع/PRs، نتائج CI، وحجم artifact الحالي.
2. **P0/P1:** مراجعة الحفظ والشبكة والأسرار والتدفق غير الموثوق؛ لا تضف خدمة خارجية قبل تحديد الحاجة.
3. **اختبارات المنطق:** سد الفجوات حول الحركة/القتال/الحوار/المهمات والحفظ باختبارات حتمية.
4. **QA build:** تشغيل الأحداث والتقارير على هاتف فعلي، ثم جمع JSON بموافقة المختبِر.
5. **الأداء والاستقرار:** قياس FPS وp95 والذاكرة والإقلاع والحجم على جهاز مستهدف وجلسة طويلة.
6. **UAT:** تحقق يدوي من Android وWeb والشبكة والأصول، مع تمييز المسارات غير المدعومة.
7. **بوابة الإصدار:** لا تعتمد المرشح حتى تتوافر أدلة كل بوابة، وتُراجع النتائج على نفس SHA.

## 10. قالب سجل نتيجة

| الحقل | القيمة المطلوبة |
|---|---|
| Test / Scenario ID | معرف ثابت |
| Commit / Build | SHA ورقم/رابط تشغيل CI |
| Platform | Android/Web/Headless + الجهاز والنظام عند الحاجة |
| Preconditions | الحالة والبيانات الابتدائية |
| Steps | خطوات قابلة لإعادة الإنتاج |
| Expected / Actual | نتيجة متوقعة ونتيجة فعلية |
| Status | PASS / FAIL / BLOCKED / NOT RUN |
| Evidence | تقرير أو log أو لقطة منقحة |
| Issue / Fix | رابط العيب وcommit الإصلاح |
| Retest | نتيجة إعادة الاختبار وتاريخه |
