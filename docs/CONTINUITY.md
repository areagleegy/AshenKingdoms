# سجل استمرارية المشروع — ممالك الرماد

- تاريخ اللقطة: 2026-10-23
- المستودع: https://github.com/areagleegy/AshenKingdoms
- الغرض: حفظ نقطة استئناف هندسية وقرارات موثقة عند الانتقال بين جلسات العمل.
- طبيعة الوثيقة: لقطة قابلة للتحديث؛ ليست سجلًا حرفيًا للمحادثات ولا بديلًا عن GitHub Issues/PRs أو نتائج CI.

## قاعدة مصدر الحقيقة

1. الكود وموارد Godot وملفات `.github/workflows/` هي المرجع للسلوك وخطوات التحقق الفعلية.
2. أوصاف PRs والقضايا تثبت القرارات والنطاق المكتوبين، لكنها لا تثبت نجاح الاختبارات.
3. سجّل نتيجة الاختبار فقط إذا شُغّل فعلًا، واربطها بالـ commit والـ CI run.
4. لا تعتبر بناء APK أو Web إثباتًا لقبول جهاز حقيقي أو جاهزية إنتاجية.
5. لا تُخزن مفاتيح API أو التوقيع أو كلمات المرور أو بيانات اعتماد في هذه الوثيقة.
6. هذه الوثيقة لا تدعي احتواء كل المحادثات التاريخية؛ يجب تصدير المحادثات الأصلية والاحتفاظ بها منفصلة قبل حذفها.

## الحالة العامة حسب الوثائق الموجودة

وفق README و`docs/PROJECT_STATUS_AR.md` المقروءين في تاريخ اللقطة:

- اللعبة نموذج أولي ثلاثي الأبعاد مبني باستخدام Godot 4.6 وGDScript.
- توجد حلقة لعب فردي تجريبية تشمل الحركة والقتال والصحة والأعداء والجرد والتدرج ومهمة وحفظًا محليًا.
- ملف الحفظ المحلي: `user://savegame.json`.
- توجد ساحة شبكة تجريبية باستخدام ENet على Desktop وAndroid؛ نجاح اختبار loopback لا يثبت أمان الشبكة العامة أو جاهزيتها الإنتاجية.
- مسار Web الحالي يدعم اللعب الفردي؛ اللعب الجماعي في Web غير مدعوم في التصدير الحالي.
- ينتج CI ملف APK تجريبيًا ARM64، لكن القبول على هاتف فعلي والتوقيع الإنتاجي لا يزالان بوابتين منفصلتين.
- حزم المحتوى الاختيارية لها بنية أولية للتحقق والتوقيع والتثبيت؛ التنزيل الإنتاجي معطل افتراضيًا.
- سجل الأصول لا يعني أن كل الأصول الفنية النهائية موجودة أو مرخصة ومكتملة.
- يجب مراجعة نتائج CI الفعلية المرتبطة بالالتزام الحالي قبل إصدار أي حكم على نجاح الاختبارات.

## نقطة الاستئناف المؤكدة: PR #95

الرابط: https://github.com/areagleegy/AshenKingdoms/pull/95  
العنوان المقروء: `refactor: extract shared progression threshold rule`  
الحالة عند الفحص: مفتوح.

النطاق:
- استخراج معادلة الخبرة المشتركة إلى `ProgressionRules.required_xp_for_level(level)`.
- استعمالها من `ProgressionManager` و`network_avatar`.
- إبقاء المعادلة كما هي: المستوى 1 يحتاج 100 XP، والعتبة تزداد 50 XP لكل مستوى.
- تغطية المستويات 1–50 واختبار نتائج ممثلة عند المستويات 1 و2 و3 و50.
- لا تُغيّر سياسات التدرج القائمة داخل هذا PR.

التحقق المطلوب وفق وصف PR:
- اختبار مجال التدرج.
- اختبار انحدار اللعب.
- اختبار smoke للقتال الشبكي.
- مراجعة نتائج CI على الالتزام المحدث؛ لا يُدّعى نجاحها قبل ظهور نتيجة فعلية.

## القضية المنفصلة #96

الرابط: https://github.com/areagleegy/AshenKingdoms/issues/96  
العنوان: `Align progression level bounds and XP-at-cap behavior`.

تحتوي القضية على ثلاثة قرارات معلقة:
1. سياسة المستويات غير الصالحة `level <= 0`، بما في ذلك الإسناد المباشر الذي يتجاوز تطبيع `ProgressionManager.restore_state()`.
2. توحيد سياسة الحد الأقصى: `ProgressionManager.max_level` افتراضيًا 50 وقابل للضبط حتى 100، بينما `network_avatar.MAX_LEVEL` ثابت عند 50.
3. توحيد السلوك المقصود للخبرة الزائدة عند الحد الأقصى: المدير المحلي يحتفظ بالخبرة حتى العتبة الحالية، بينما `network_avatar.server_grant_experience()` يصفر الخبرة.

معايير الإغلاق:
- توثيق القرار لكل حالة.
- إضافة اختبارات انحدار مركزة للمسارات المتأثرة.
- تنفيذ التغييرات في PR لاحق مستقل، دون توسيع PR #95.

## الأمن والحفظ

تذكر ملاحظات المشروع السابقة تقوية SaveSystem والتحقق من المخطط والكتابة الذرية والنسخ الاحتياطية والترحيل وحدود الحجم، واختبارات توافق تستخدم بيانات فعلية من `main.gd`. هذه الوثيقة لا تؤكد أن جميع هذه الضوابط قد اجتازت تدقيقًا حاليًا؛ يجب مراجعة الكود والاختبارات والنتائج.

معايير تحقق مهمة:
- التعامل الآمن مع ملفات الحفظ التالفة والمخططات غير المدعومة.
- عدم إتلاف آخر حفظ سليم عند فشل الكتابة.
- اختبار الاستعادة والترحيل وحدود الأحجام.
- اختبار بيانات فعلية ومسارات فشل قابلة للتكرار.
- تسجيل الدليل والالتزام الذي تم اختباره.

## الإصدار والمنصات

أهداف المشروع في الوثائق الحالية هي Android وWeb، مع لعب فردي وجماعي مستهدف. لكن الوضع ليس متكافئًا بين المنصات: ENet التجريبي لا يعمل في تصدير Web الحالي. يلزم اختبار APK على هاتف حقيقي، واختبار Web منشورًا عبر HTTP/HTTPS، ومراجعة الأصول والتراخيص، والتحقق من التوقيع والإعدادات قبل اعتبار الإصدار جاهزًا.

لا يُعلن دعم PlayStation أو أي منصة إضافية قبل إثبات دعم المحرك والأدوات والتراخيص ومتطلبات المنصة والبناء والاختبار.

## خريطة الأنظمة والملفات الأساسية

استنادًا إلى `docs/TECHNICAL_ARCHITECTURE.md` و`project.godot`:

- نقطة البدء: `scenes/ui/MainMenu.tscn`.
- مشهد اللعب الفردي: `scenes/boot/Main.tscn`.
- ساحة الشبكة: `scenes/network/MultiplayerArena.tscn`.
- Autoloads: `DialogueManager` من `scripts/dialogue/dialogue_manager.gd`، و`ContentManager` من `scripts/content/content_manager.gd`، و`NetworkManager` من `scripts/core/network_manager.gd`.
- المنطق الأساسي: `scripts/core/main.gd`، `scripts/core/progression_manager.gd`، `scripts/core/quest_manager.gd`، `scripts/core/save_system.gd`.
- اللاعب والأعداء والمكونات القابلة لإعادة الاستخدام موجودة ضمن `scripts/player/` و`scripts/enemies/` و`scripts/components/`.
- واجهات HUD والحوار والقائمة في `scripts/ui/` ومشاهد UI المقابلة.
- ملفات المحتوى القابل للتنزيل موجودة في `scripts/content/`، وأدوات بناء وتوقيع الحزم في `tools/package_content.py` و`tools/sign_content_catalog.py`.

هذه خريطة أولية من الوثائق وليست بديلًا عن فحص الملفات قبل أي تغيير. عند اختلاف الوثيقة عن الكود، يُراجع الكود ويُحدّث التوثيق في نفس PR.

## الحفظ المحلي والتدرج والمهام والحوار

- الحفظ الحالي يستخدم JSON في `user://savegame.json`.
- بيانات الحفظ ينبغي أن تستخدم قيمًا بسيطة ومعرّفات عناصر، لا مراجع موارد Godot مباشرة.
- اللعب الفردي يتضمن حركة وقتالًا وصحة وأعداء وجردًا وجرعات وخبرة ومستويات ومهمة تجريبية.
- الحوار وNPC محليان تجريبيان؛ أعلام الحوار تحفظ ضمن بيانات الحفظ تحت `dialogue.flags`.
- آثار الحوار تمر عبر `DialogueManager._apply_effects()` في اللعب الفردي. لا تفترض أنها متصلة بساحة الشبكة.
- اختبارات اللعب المذكورة في `docs/TEST_PLAN.md` تشمل ترقية المستوى، ومنح مكافأة المهمة مرة واحدة، واستعادة المهمة، وكتابة JSON ورفض JSON غير صالح، والحفظ والتحميل. يجب قراءة نتائج التشغيل الفعلية قبل تسجيل نجاحها.

## الشبكة وحدود الثقة

مرجع التشغيل: `docs/NETWORKING.md`، ومرجع المخاطر: `docs/NETWORK_THREAT_MODEL_AR.md`.

- ساحة ENet منفصلة عن حلقة اللعب الفردي، ويبدأ المضيف عبر `NetworkManager.start_host()` من مسار القائمة.
- العميل يرسل نية الإدخال، بينما تُحسب الحركة والضرر والصحة والخبرة ومكافآت المهمة على الخادم في النموذج التجريبي.
- اختبار loopback المحلي لا يثبت العمل عبر الإنترنت، ولا مصادقة المستخدمين، ولا أمان خادم عام.
- لا توجد مصادقة حسابات أو حفظ شبكي دائم أو نظام مكافحة غش إنتاجي كامل حسب الوثائق.
- لا تتصل ساحة الشبكة حاليًا بنظام الحوار والجرد والجرعات المحليين.
- ENet معطل في تصدير Web؛ يتطلب دعم Web متعدد اللاعبين ناقلًا متوافقًا مع المتصفح وخادمًا ملائمًا.
- لا تستخدم النسخة الحالية لخادم عام إنتاجي أو اقتصاد حقيقي أو بيانات حسابات.

### بوابات الإصدار غير المثبت اكتمالها

- اختبار APK على هاتف Android فعلي، مع تسجيل الجهاز وإصدار النظام والنتيجة.
- نشر Web عبر HTTP/HTTPS واختباره في المتصفحات المستهدفة.
- اختبار الشبكة بين جهازين فعليين إذا كان الإصدار يعلن دعم الشبكة على تلك المنصة.
- تحديد هوية التطبيق وتوقيع الإنتاج وقناة التوزيع.
- فحص تراخيص الأصول وإسنادها ومراجعة الملفات الفعلية، لا سجل الأصول وحده.
- مراجعة CI على رأس PR نفسه وربط النتيجة بالـ commit والـ artifact.
- قبول الإصدار بقرار موثق. نجاح التصدير وحده لا يثبت قبول المستخدم أو الأداء الفعلي.

## الأصول وحزم المحتوى

- سجل الأصول: `assets/asset_manifest.json`، وإسناد الأصول: `docs/ASSET_CREDITS.md`.
- السياسة تتطلب التحقق من الترخيص والمصدر والسماح بالاستخدام التجاري وإعادة التوزيع؛ كون الأصل مجانيًا لا يكفي.
- سجل الأصول الحالي لا يثبت اكتمال مجموعة فنية نهائية.
- حزم المحتوى الاختيارية لها تحقق توقيع RSA-SHA256 وبصمات SHA-256 وحدود للمسارات والأحجام والاعتماديات بحسب الوثائق.
- تنزيل المحتوى مؤجل ومعطل افتراضيًا؛ لا يوجد CDN إنتاجي أو مفتاح عام مضبوط أو حزم فعلية منشورة وفق `content/README.md`.
- لا يُضمّن المفتاح الخاص في المستودع أو اللعبة أو CI. يجب أن تبقى اللعبة قابلة للعب دون إنترنت عند عدم تهيئة خدمة المحتوى.
- استئناف التنزيل وفحص المساحة على Android وإدارة إصدارات الحزم ما زالت تحتاج إلى تحسين واختبار قبل اعتماد النظام للإنتاج.

### Issue #20 — بوابة قبول الإصدار
https://github.com/areagleegy/AshenKingdoms/issues/20

بوابة قبول مستقلة عن نجاح CI، وتشمل:
- تثبيت APK على جهاز Android فعلي وتوثيق الجهاز والنظام.
- اختبار Web مستضاف عبر HTTP/HTTPS في المتصفحات المستهدفة.
- مراجعة الأصول والتراخيص والإسناد وتحديد الأصول المؤقتة.
- تحديد اسم التطبيق ومعرّف Android وقناة التوزيع وإصدار التطبيق.
- إعداد توقيع الإنتاج عبر أسرار CI المحمية دون تخزين keystore أو كلمات مرور في Git.
- وضع أهداف كمية للحجم والأداء قبل القياس، وتسجيل checksum والالتزام وقرار قبول الإصدار.

تتضمن القضية لقطة تاريخية من 20 أكتوبر 2026 عن APK تجريبي حجمه 27,899,706 بايت وبصمة SHA-256، وعن Artifacts ذات مدة احتفاظ محدودة. هذه بيانات تاريخية مرتبطة بتشغيل وcommit محددين وليست قياسًا للـ APK الحالي. تحقق من انتهاء صلاحية Artifacts ومن تشغيل البناء الحالي قبل الاعتماد عليها.

### Issue #21 — ناقل اللعب الجماعي على Web
https://github.com/areagleegy/AshenKingdoms/issues/21

- الهدف المعتمد يشمل اللعب الفردي والجماعي على Android وWeb.
- ENet الحالي غير متاح في تصدير Web؛ لا يُعلن دعم اللعب الجماعي في المتصفح حتى اختبار عميل متصفح حقيقي ضد نقطة WSS منشورة.
- تسجل القضية PR #24 كتنفيذ تجريبي لمسار WebSocket للانضمام من المتصفح، مع تعطيل الاستضافة من المتصفح. يلزم التحقق من حالة PR #24 الحالية وعدم افتراض دمجه أو نشره.
- يجب اختبار الجلسة والانضمام والمغادرة والانقطاع والرسائل غير الصالحة ومزامنة الحالة، ثم المصادقة وحدود المعدل ومقاومة الإساءة والاختبار عبر الأجهزة.
- لا تكفي اختبارات loopback المحلية لإغلاق بوابة المتصفح أو الأمان التشغيلي.

### Issue #41 — نموذج اللاعب النهائي
https://github.com/areagleegy/AshenKingdoms/issues/41

- تصف القضية أن النموذج الحالي يستخدم بديلًا هندسيًا مؤقتًا عند غياب `assets/characters/player/player.glb`.
- المطلوب أصل GLB أصلي مرخّص، مع هيكل وحركات أساسية وتوثيق المقياس والمحور وعدد المثلثات والمواد ودقة الخامات وحجم الملف.
- يجب تسجيل المصدر والترخيص والإسناد وبصمة SHA-256 في سجل الأصول.
- لا تستخدم خدمات توليد مدفوعة ما دامت سياسة `assets/asset_manifest.json` تمنع واجهات التوليد المدفوعة.
- لا تستبدل البديل المؤقت قبل إثبات استيراد النموذج والتحريك واختبارات اللعب وقياس الأداء على Android.
