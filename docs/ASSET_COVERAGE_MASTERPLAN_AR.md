# خطة التغطية الشاملة للأصول المرئية والصوتية والحزم — AshenKingdoms
تاريخ التدقيق: 2026-10-21  
الحالة: خطة تنفيذ وتحقق؛ لا تعني أن كل الأصول أدناه موجودة أو معتمدة.  
المحرك المستهدف: Godot 4.6؛ الأولوية Android، مع المحافظة على Web حيثما يدعمه المشروع.

## 1. قواعد لا يجوز تجاوزها
1. لا يُدمج أي أصل إلى `main` قبل التحقق من المصدر والترخيص وحقوق الاستخدام التجاري وإعادة التوزيع والتعديل والإسناد.
2. لا تعتبر نتيجة توليد أو نموذج أولي أصلًا نهائيًا. يلزم اختبار استيراد وتشغيل ومراجعة فنية.
3. لا تُشترى أرصدة أو تُستدعَ خدمات مدفوعة دون موافقة صريحة على التكلفة.
4. لا تُضمّن مفاتيح API أو أسرارًا في المستودع أو مطالبات التوليد أو ملفات اللعبة.
5. كل أصل له معرف ثابت وسجل manifest وبصمة SHA-256 وحجم ونسخة ومصدر وترخيص واختبارات وموضع استخدام.
6. لا تُستبدل ملفات موجودة بصمت؛ استخدم فرعًا مستقلًا وPR، واحتفظ بإمكانية الرجوع.
7. لا تُعتبر لقطة أو ملفًا ناتجًا من أداة خارجية موجودًا في المستودع إلا بعد تصديره والتحقق منه ورفعه.

## 2. الوضع المرصود
- `assets/asset_manifest.json` في الفرع الافتراضي يسجل أيقونة SVG للمشروع فقط، ويشترط الترخيص التجاري وإعادة التوزيع.
- PR #49 مفتوح كمسودة: https://github.com/areagleegy/AshenKingdoms/pull/49 . يصف أيقونات SVG، وGLB أوليًا للاعب وشبح الرماد بلا Skeleton/Animation، وبيئة أولية وخامة أرضية إجرائية واختبارات CI. التقرير داخل PR يذكر أن آخر رأس موثق اجتاز Validate وBuild، بينما إعادة التحقق من رأس التوثيق كانت قيد التنفيذ في آخر فحص؛ يجب إعادة التحقق من حالة CI الحالية قبل الاعتماد.
- PR #50 مفتوح كمسودة: https://github.com/areagleegy/AshenKingdoms/pull/50 . يصف 13 مؤثر WAV إجرائية وموسيقى حلقية 8 ثوانٍ وأجواء رياح ومدير صوت؛ لا يوجد استماع بشري أو اختبار هاتف فعلي موثق.
- PR #49 و#50 متداخلان في ملفات الإعداد والمانيفست ومدير اللعبة واللاعب والعدو وHUD وCI. يجب إجراء دمج منسق وتوحيد واجهة الصوت قبل اعتماد أي منهما.
- مشروع Thrixel الحالي يبدأ بلا أصول مولدة مسجلة. مشهد Spline الأولي نموذج اتجاه فني/بلوك آوت وليس ملف لعبة GLB جاهزًا. لم يُثبت تصديره أو استيراده إلى Godot.
- لذلك لا يُدّعى اكتمال الشخصيات المتحركة أو الصوت النهائي أو التحقق على هاتف فعلي.

## 3. خريطة تغطية الأصول (سجل القبول)
الأولوية: P0 ضروري لنسخة لعب قابلة للاختبار؛ P1 جودة ووضوح؛ P2 توسعة محتوى. حدّد حالة كل عنصر في manifest: `planned`, `generated`, `import-tested`, `runtime-tested`, `approved`, `blocked`.

### A. الشخصيات والأنيميشن
- P0 اللاعب: نموذج منخفض/متوسط التفاصيل، Skeleton صحيح، idle/walk/run/jump/attack/hit/death، نقاط تثبيت السلاح، تصادم منفصل.
- P0 عدو أساسي: silhouette مميز، rig متوافق، idle/approach/attack/hit/death، مسافات وحجم متسقان.
- P1 فئات أعداء: سريع، ثقيل، بعيد المدى، طيفي؛ تختلف بالحركة والقراءة البصرية لا بالألوان فقط.
- P1 خامات بديلة/ملابس/دروع/خوذة مع فصل الأجزاء القابلة للتبديل دون مضاعفة draw calls بلا داع.
- P2 NPCs، شخصيات حوار، زعماء ومجموعات حركة إضافية.
قبول الشخصية: لا أخطاء عظام/تطبيع/أوزان، لا انزلاق قدم ظاهر في الدورة الأساسية، لا اختراق حاد للسلاح، مقياس ومحور أمامي موثقان، أسماء clips ثابتة، واختبار import + animation playback.

### B. الأسلحة والدروع والأغراض
- P0 سيف البداية، درع/أداة دفاع، جرعة، غنيمة قابلة للالتقاط.
- P1 فئات سلاح إضافية وقطع دروع قابلة للتركيب، خامات معدن/جلد/قماش مشتركة.
- P2 عناصر نادرة، آثار، مفاتيح وأغراض مهام.
قبول: pivot صحيح، collider منفصل ومبسط، LOD/مستوى تفاصيل مناسب عند الحاجة، خامات قليلة قابلة لإعادة الاستخدام، وتطابق الحجم مع يد الشخصية.

### C. العالم والبيئات
- P0 ساحة البداية: أرض، حواف آمنة، مسار واضح، نقطة spawn، حواجز وتصادمات.
- P1 أطلال، بوابة، أعمدة مكسورة، ركام، صخور، رموز برونزية، نباتات مقتصدة، sky/fog قابلان للضبط.
- P1 منطقة داخلية/كهف وممرات انتقال.
- P2 مناطق متميزة بيئيًا، معالم بعيدة، زينة سردية وتنوع إضاءة.
قبول: حدود لعب واضحة، لا تصادمات مفقودة أو غير مرئية، تكرار بصري محدود، واختبار أداء GPU/CPU على جهاز Android فعلي.

### D. المؤثرات المرئية VFX
- P0 ضربة سيف/وميض إصابة/علامة ضرر واضحة.
- P1 شرر واصطدام معدن، غبار خطوات، رماد متطاير، موت عدو، أثر جرعة.
- P2 مؤثرات زعيم وطقس وبيئات متحركة.
قبول: لا تسرّب Nodes/Particles، حدود عمر وحجم واضحة، عدد جسيمات محدود على Android، وبديل بصري منخفض التكلفة.

### E. واجهة المستخدم والأيقونات
- P0 أيقونات الحركة والهجوم والدفاع والجرعة والإيقاف؛ حالات hover/pressed/disabled إذا لزم.
- P0 HUD للصحة والطاقة والمهام ومؤشرات التفاعل.
- P1 شاشات inventory/equipment/quests/settings/audio/accessibility.
- P2 رسوم توضيحية وخلفيات للقوائم.
قبول: SVG/مصدر قابل للتعديل حيث أمكن، تباين واضح، دعم أحجام شاشات متعددة، وعدم الاعتماد على نص داخل صورة للأسماء الديناميكية.

### F. الصوت
- P0 SFX: ضربة، اصطدام، إصابة لاعب، إصابة عدو، موت، التقاط غرض، جرعة، زر واجهة، نجاح/فشل مهمة.
- P1 خطوات متعددة للأسطح، parry مستقل، سحب سلاح، رياح ومحيط، طبقات موسيقى منفصلة.
- P2 حوار عربي مسجل، أصوات متنوعة للأعداء، موسيقى زعيم ومناطق إضافية.
- إنشاء AudioManager واحد بواجهات واضحة، ناقلات Master/Music/SFX/Ambience/Voice، كتم ومستويات محفوظة، تحميل كسول/تخزين مؤقت محدود، ووقف الأصوات عند تحرير المشهد.
قبول: الاستماع بسماعة الهاتف وسماعات الرأس، اختبار loop/no-click، عدم clipping، موازنة loudness، قياس مدة/قنوات/sample rate/peak/RMS، ومراجعة حقوق التسجيل/الصوت الاصطناعي. لا تعتمد موسيقى قصيرة قبل فحص تكرارها عمليًا.

### G. الموسيقى والحوار
- P0 طبقة استكشاف قابلة للتكرار مع fade-in/out.
- P1 طبقة قتال انتقالية وموسيقى قائمة/قائمة رئيسية.
- P2 موسيقى زعماء ومناطق، حوار عربي، captions وبدائل لضعاف السمع.
قبول: انتقالات غير مفاجئة، مستوى متوازن تحت SFX، loop points سليمة، وتوثيق مصدر كل ملف.

## 4. حزم ومكونات إضافية: سياسة اختيار
افحص الإضافات المفعّلة في `project.godot` قبل إضافة أي شيء جديد، وبالأخص إضافات Ashen Asset Bridge وAshen Free Asset Pipeline. لكل إضافة سجل: الرابط الرسمي، الإصدار/commit، الترخيص، التبعيات، صلاحيات الملفات/الشبكة، نشاط الصيانة، الثغرات المعروفة، حجم البناء، سبب الاستخدام، وخطة الإزالة.
- استخدم أدوات Godot المدمجة وglTF/GLB قدر الإمكان لتقليل التبعيات.
- Blender مناسب للتحرير/الـrig والـLOD والمعالجة الدفعية عند الحاجة؛ لا تضف ملفات مصدر ضخمة إلى بناء اللعبة.
- استخدم أدوات ضغط/تحويل الصوت الموثوقة المتاحة في بيئة البناء، مع إبقاء المصدر الأصلي خارج الحزمة النهائية إن سمح الترخيص.
- لا تضف مكتبات runtime لمجرد أتمتة مهمة يمكن تنفيذها بأداة build-time.
- افحص كل تنزيل بمصدره وبصمة SHA-256 والترخيص، وامنع الأصول ذات الترخيص المجهول.

## 5. ميزانيات ابتدائية — أهداف قابلة للقياس وليست ضمانات
- الشخصية الرئيسية: ابدأ بنحو 8k–20k triangles للنموذج المتحرك، وقلّل إذا لم تظهر التفاصيل على شاشة الهاتف.
- عدو عادي: أقل من اللاعب متى أمكن؛ اختبر مجموعات متعددة في المشهد لا النموذج المنفرد فقط.
- خامات الشخصيات: 1K هدف ابتدائي؛ 512px للأغراض الصغيرة؛ لا ترفع الدقة دون فائدة مرئية.
- اجعل عدد material slots محدودًا، أعد استخدام الخامات، واضغط textures وفق صيغ تدعمها المنصة.
- فضّل instancing للأجسام المتكررة وLOD فقط حين يثبت القياس فائدته.
- الصوت: استعمل mono للأصوات الموضعية التي لا تحتاج stereo؛ اختر معدل العينة والترميز بعد اختبار جودة/حجم على المنصتين.
- احتفظ بميزانية APK وWeb محددة في CI، وسجّل حجم كل بناء وبصمته ومقارنة التغيير عن خط الأساس.
- أهداف FPS والذاكرة تُحدّد بعد قياس أجهزة مستهدفة حقيقية؛ لا تخترع نتائج قياس غير موجودة.

## 6. خط سير التحقق الآلي
1. تحقق schema للـmanifest، وتفرّد IDs والمسارات، وعدم وجود مسارات مفقودة.
2. SHA-256 والحجم ونوع MIME، وكشف الملفات المكررة/المتطابقة.
3. تحقق GLB/glTF: JSON/chunks، الصور المضمنة، meshes/materials/nodes/skins/animations، scale/axis، أسماء المقاطع.
4. استيراد headless إلى نسخة Godot المطابقة للمشروع؛ افحص أخطاء الاستيراد والتحذيرات.
5. اختبارات المشهد: وجود الأصول في المواضع المتوقعة، تصادمات أساسية، تشغيل الأنيميشن والصوت، وتنظيف العقد/الجسيمات.
6. اختبارات الصوت: WAV header، sample rate/channels/duration/peak/RMS، عدم الصمت الكامل، clipping، manifest، والترخيص.
7. بناء Android وWeb في CI؛ لا تعتبره نجاحًا إلا مع روابط artifacts ونتائج واضحة للرأس نفسه.
8. اختبار runtime: spawn، قتال، موت، عودة للمشهد، حفظ الإعدادات، انقطاع/عودة الشبكة إذا كان المسار متصلًا.
9. مراجعة بشرية بصرية وسمعية، ثم اختبار على جهاز Android فعلي وقياس FPS/حرارة/ذاكرة/استهلاك بطارية.
10. لا تعتمد تلقائيًا على اختبارات AI وحدها؛ استخدمها لتوليد حالات واكتشاف شذوذ، ويظل القبول مبنيًا على نتائج قابلة لإعادة الإنتاج.

## 7. سجل الأصول المطلوب
لكل أصل: `id`, `category`, `path`, `format`, `source_url`, `creator`, `license`, `license_url`, `commercial_use`, `redistribution_allowed`, `modification_allowed`, `attribution`, `sha256`, `bytes`, `dimensions_or_duration`, `triangle_count`, `texture_budget`, `target_scenes`, `dependencies`, `generation_tool_and_model`, `generation_cost`, `validation_status`, `test_evidence`, `reviewer`.
لا تضع أي قيمة مفترضة للترخيص أو البصمة أو الاختبار؛ استخدم null/unknown حتى التحقق.

## 8. بوابات الإصدار
- Gate A: الترخيص والمصدر موثقان.
- Gate B: سلامة الملف وبصمته وفحصه الأمني.
- Gate C: استيراد ناجح في Godot.
- Gate D: استخدام فعلي في مشهد/لعب واختبار regression.
- Gate E: أداء مقبول على Android وWeb حيث ينطبق.
- Gate F: مراجعة بشرية ودمج عبر PR.
يُحظر وصف الأصل بأنه production-ready قبل اجتياز البوابات المناسبة.

### نتيجة مراجعة الإضافات المفعّلة
- `Ashen Asset Bridge` و`Ashen Free Asset Pipeline` إضافتان محليتان ضمن `addons/`، وليستا حزمًا خارجية مثبتة من مدير إضافات في الحالة التي فُحصت.
- المراجعة الساكنة للملفين `plugin.gd` لم تُظهر طلبات شبكة أو استدعاءات API مدفوعة. الأولى تحمّل `player.glb` وتعدّ Mesh/Skeleton/Animation nodes، والثانية تجرد امتدادات الملفات وتفتح مجلدات محلية عبر `OS.shell_open`.
- ملاحظة جودة: رسالة الإضافة الأولى تشير إلى استخدام أداة Meshy محلية لتوليد GLB؛ هذه إشارة غير دقيقة/ملتبسة لأن الإضافة نفسها لا تنفذ التوليد. يجب تغيير النص إلى تعليمات محايدة عن استيراد GLB والتحقق من الترخيص قبل اعتبار الإضافة مكتملة.
- ملاحظة تغطية: جرد `Ashen Free Asset Pipeline` يعدّ الملفات ذات الامتدادات المدعومة فقط، ولا يتحقق من سلامة المحتوى أو الترخيص أو التكرار أو الملفات المتداخلة/المخفية. النص في الإضافة يذكر هذا القيد؛ لا تستخدم العدد باعتباره عدد الأصول المعتمدة.
- تظل الإضافتان مفعّلتين في `project.godot` على main. يلزم اختبار فتح المحرر، تعطيل/تفعيل الإضافات، وعدم وجود أخطاء @tool أو آثار جانبية على تصدير Android/Web قبل الاعتماد النهائي.

### عائق الدمج الصوتي المؤكد من ملفات المصدر
