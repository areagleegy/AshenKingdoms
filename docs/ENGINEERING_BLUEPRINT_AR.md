# الدستور الهندسي وخارطة التنفيذ — ممالك الرماد

> **نوع الوثيقة:** قرار معماري وخطة تنفيذ تدريجية.  
> **المحرك الحالي:** Godot 4.6 وGDScript.  
> **حدود الوثيقة:** تصف الاتجاه المستهدف وقواعد التطوير؛ ولا تعني أن كل مرحلة أدناه نُفذت أو اجتازت الاختبارات.

## 1. الهدف والقرارات الأساسية

نطوّر المشروع تدريجيًا من نموذج أولي قابل للعب إلى لعبة يمكن صيانتها واختبارها وتوسيعها، دون إعادة كتابة شاملة أو إدخال خدمات لا يحتاجها نطاق الإصدار الحالي.

1. **الاحتفاظ بـ Godot وGDScript.** لا يوجد مبرر حالي لإعادة بناء المشروع بـ C# أو نقل المحرك.
2. **اعتماد Modular Monolith بحدود واضحة.** تبقى الأنظمة داخل مشروع Godot واحد، مع فصل قواعد اللعبة عن تنسيق المشاهد وعن الشبكة والتخزين.
3. **عدم فرض ECS على المشروع كله.** مشاهد Godot وعُقده مناسبة للعرض والفيزياء ودورة الحياة. نستخدم مكونات قابلة لإعادة الاستخدام حيث يوجد تكرار فعلي، ولا نضيف إطار ECS لمجرد اتباع نمط معماري.
4. **الهجرة تدريجية.** ننقل قاعدة منطقية واحدة في كل مرة، ونحافظ على سلوك اللعبة باختبارات انحدار قبل تغيير الأنظمة التالية.
5. **الخادم مرجع حالة اللعب الجماعي.** رسائل العميل تمثل نوايا أو إدخالات، وليست حقائق موثوقة عن الصحة أو الضرر أو الخبرة أو الغنائم.
6. **الخطة ليست إثبات تنفيذ.** مصدر الحقيقة للحالة الحالية هو الشفرة وملفات CI ونتائج التشغيل للـ commit المقصود.

## 2. خريطة الطبقات والمسؤوليات

| الطبقة | المسؤولية | مكانها الحالي أو المستهدف |
|---|---|---|
| Domain — قواعد اللعبة | قواعد حتمية مثل صلاحية الهجوم، حساب الضرر، تغيّر حالة المهمة والتحقق من سعة الجرد؛ دون قراءة ملفات أو معرفة بالواجهة | طبقة مستهدفة تُضاف تدريجيًا تحت **scripts/domain/** |
| Application / Orchestration | تنسيق حالات الاستخدام وربط القواعد بالمشهد والأنظمة | أجزاء منها موجودة في **scripts/core/** ومديري الأنظمة الحاليين |
| Adapters / Integrations | التعامل مع واجهات المحرك والشبكة وملفات الحفظ وحزم المحتوى | **scripts/networking/** و**scripts/content/** و**scripts/core/save_system.gd** |
| Presentation | المشاهد وHUD والتحكم والحوارات المعروضة للمستخدم | **scenes/** و**scripts/ui/** |
| Game objects | سلوك الشخصيات والأعداء وNPC والمكونات المرتبطة بعقد Godot | **scripts/player/** و**scripts/enemies/** و**scripts/npc/** و**scripts/components/** |
| Content & Assets | الموارد والملفات الفنية وبيانات المصدر والترخيص وأدوات التحقق | **resources/** و**assets/** و**content/** و**tools/** |
| Quality gates | اختبارات المنطق والتكامل وفحوص الاستيراد والبناء | **tests/** و**.github/workflows/** |

هذه حدود مسؤوليات وليست أمرًا بنقل كل الملفات الآن إلى مجلدات جديدة. لا ننشئ مجلدًا فارغًا لمجرد أن الرسم المعماري يحتويه.

## 4. قواعد الاعتماد بين الطبقات

- قواعد Domain لا تعتمد على واجهة المستخدم أو المشاهد أو NetworkManager أو DialogueManager أو ContentManager، ولا على نظام ملفات أو اتصال شبكي.
- تجنّب داخل Domain استخدام get_tree() أو get_node() أو FileAccess أو rpc() أو MultiplayerAPI أو الوصول إلى عقد واجهة. يمكن استخدام أنواع القيم الأساسية في Godot عند الحاجة.
- منسقو الحالات يربطون المدخلات بالقواعد والتكاملات. لا تُنسخ معادلة الضرر أو شروط المكافأة في الواجهة والعميل والخادم كلٌ على نحو مختلف.
- طبقة الشبكة تتحقق من هوية النظير المرسل وملكية الكيان وحالة اللعب وحدود المعدل والمدى والمهلة قبل تمرير الفعل إلى قاعدة اللعبة.
- طبقة العرض تعرض الحالة وتحول تفاعل المستخدم إلى أوامر؛ لا تقرر وحدها منح خبرة أو مكافأة ذات قيمة شبكية.
- تُحفظ التعريفات الثابتة، مثل بيانات غرض أو مهمة، كموارد بيانات عند ملاءمتها. أما الحالة المتغيرة لكل لاعب فيجب أن يكون لها مالك واضح، وألا يُشارك مورد متغير بين كيانات مستقلة دون قصد.
- لا نضيف واجهات تجريد كثيرة لمجرد النمط. نضع حدًا أو عقدًا حين توجد أكثر من طريقة تنفيذ أو حاجة فعلية للاختبار والاستبدال.

## 5. استراتيجية فصل منطق اللعبة

ابدأ بأقل قاعدة ممكنة المخاطر، وكرر دورة صغيرة:

1. حدد سلوكًا قائمًا في الشفرة واكتب اختبارًا يثبت النتيجة الحالية والحدود المهمة.
2. استخرج القاعدة إلى دالة أو كائن صغير حتمي تحت **scripts/domain/<system>/**، مع إدخال القيم اللازمة كوسائط بدل قراءة المشهد مباشرة.
3. اجعل المنسق الحالي يستدعي القاعدة الجديدة مع الحفاظ على نقطة الدخول وسلوك المستخدم.
4. أضف اختبارات للحالات الطبيعية والحدود والقيم غير الصالحة وتكرار الطلبات.
5. شغّل الاختبارات المرتبطة واختبارات الانحدار، ثم حدث الوثائق في Pull Request نفسه.
6. لا تنتقل إلى نظام آخر حتى تكون الفروق مقصودة والنتائج موثقة.

أمثلة مناسبة للفصل لاحقًا: حساب صلاحية الهجوم والضرر، قواعد سعة الجرد، انتقالات حالة المهمة، وحساب مكافأة التقدم. لا تُنقل هذه الأنظمة دفعة واحدة ولا تُستبدل قواعد اللعب الحالية قبل إضافة تغطية مناسبة.

## 6. الشبكة والأمن

### قواعد إلزامية

- يعتبر العميل غير موثوق حتى لو كان تطبيقًا رسميًا. لا يقبل الخادم قيم الصحة أو الضرر أو الخبرة أو الغنائم أو إتمام المهمة كحقائق يقررها العميل.
- يتحقق الخادم من مصدر RPC وملكية الكيان وتسلسل الحالة والتهدئة والمدى والقيم ضمن الحدود ومعدل الرسائل. ويجب رفض الإدخال غير الصالح دون إفساد حالة الجلسة.
- تعامل مع الفصل وانتهاء المهلة وإعادة الاتصال والرسائل المتكررة كحالات طبيعية يجب اختبارها.
- لا تضع مفاتيح API أو أسرار CI أو مفاتيح توقيع الحزم وAndroid في المستودع. استخدم إعدادات البيئة وأسرار GitHub المناسبة، مع أقل صلاحيات لازمة.
- لا تكتب بيانات اعتماد أو رموز جلسات أو بيانات شخصية في سجلات التصحيح. حدد ما يلزم تسجيله ومدة الاحتفاظ به قبل إضافة سجلات مركزية.
- لا تنفذ تشفيرًا مخصصًا. استخدم آليات النقل والتخزين التي يوفرها النظام المستهدف، وحدد التشفير بناءً على حدود الثقة والحاجة الفعلية.
- تحقق من الأصول والحزم الخارجية وتراخيصها كما يحدد [سجل الأصول](ASSET_CREDITS.md) و[نموذج تهديدات الشبكة](NETWORK_THREAT_MODEL_AR.md).

### الحالة الحالية والحدود

الشبكة عبر ENet ساحة تجريبية على Desktop وAndroid، وWeb لا يدعم مسار ENet الحالي. لا توجد مصادقة حسابات أو حفظ شبكي دائم أو خدمة عامة جاهزة للإنتاج. راجع [وثيقة الشبكة](NETWORKING.md) و[نطاق الإصدار](RELEASE_SCOPE_AR.md) قبل تغيير هذا الوصف.

لا تُعتمد PostgreSQL أو Redis أو gRPC أو خدمة مصادقة منفصلة تلقائيًا ضمن هذا العمل. تُدرس هذه الخيارات فقط عندما يتطلب المنتج حسابات موثوقة أو حفظًا مشتركًا دائمًا أو اقتصادًا شبكيًا؛ عندها يلزم تصميم تهديدات وتكلفة وتشغيل وترحيل مستقل.

## 7. الاختبارات وبوابات الدمج

- **Unit:** اختبارات سريعة لقواعد Domain الحتمية، بما في ذلك الحالات الحدية وعدم تكرار المكافآت.
- **Integration:** اختبار الربط مع حفظ الملفات وموارد Godot والشبكة وتثبيت حزم المحتوى والتحقق منها.
- **Smoke / Regression:** الحفاظ على مجموعة اختبارات التشغيل والانحدار الموجودة؛ لا يُحذف اختبار لتجاوز فشل دون توثيق البديل.
- **Platform acceptance:** اختبار Android على جهاز فعلي ونشر Web عبر HTTP/HTTPS واختباره في المتصفح. نجاح التصدير لا يثبت نجاح تجربة المستخدم أو الشبكة.
- **Network acceptance:** اختبار مضيف وعميل فعليين، وفصل الاتصال وإعادته، وإساءة الإدخال، وحدود الاتصالات والموارد على شبكة ممثلة.
- **Merge gate:** يجب أن تكون فحوص CI ذات الصلة بالـ commit المرشح ناجحة قبل الدمج، مع مراجعة بشرية للتغييرات الحساسة.

نسب 70/20/10 بين أنواع الاختبارات ليست هدفًا جامدًا؛ الأهم أن تبقى قواعد المجال سريعة الاختبار، وأن تغطي اختبارات التكامل نقاط الفشل الفعلية، وأن توجد اختبارات طرفية قليلة لكنها ذات قيمة.

## 8. خطة التنفيذ المرحلية

| المرحلة | العمل | معيار القبول |
|---|---|---|
| 0 — خط أساس | قراءة الكود والوثائق ونتائج CI على commit محدد | توثيق ما هو منفذ وما هو تجريبي دون ادعاء نجاح فحوص لم تُشغّل |
| 1 — أول قاعدة Domain | اختيار قاعدة صغيرة من القتال أو التقدم؛ إضافة اختبار قبل الاستخراج ثم استخراجها | القاعدة مستقلة عن الواجهة والشبكة، والاختبارات الجديدة والانحدار ناجحة |
| 2 — بيانات المحتوى | تنظيم تعريفات العناصر والمهام والخصائص القابلة للتعديل مع فصل التعريف الثابت عن الحالة المتغيرة | موارد ذات مخطط واضح، والتحقق من البيانات غير الصالحة، وعدم تغيير سلوك اللعب دون قصد |
| 3 — الحفظ والترحيل | توثيق مخطط الحفظ المحلي وإضافة رقم إصدار وترحيل آمن عند تغييره | تحميل الحفظ القديم أو رفضه برسالة واضحة؛ لا فساد صامت ولا افتراض أنه حفظ شبكي |
| 4 — تقوية الشبكة | جرد RPC، وتحديد سقوف المعدل والاتصالات، وتحسين اختبارات الانقطاع وإساءة الإدخال | أدلة اختبار قابلة لإعادة التشغيل وحدود معروفة؛ تظل الخدمة تجريبية حتى إكمال المصادقة والتشغيل الإنتاجي |
| 5 — بوابات الإصدار | اختبار الأجهزة والمتصفحات، وتدقيق الأصول، ومراجعة الأذونات والأسرار وسجل الإصدار | تقرير قبول يربط النتائج بالـ commit وبناءات المنصات الفعلية |
| 6 — خدمات خلفية عند الحاجة | تصميم هوية وحفظ دائم وخدمات موثوقة فقط إذا أصبح ذلك ضمن نطاق المنتج | نموذج تهديدات، ومخطط بيانات، ونسخ احتياطي وترحيل، ومراقبة واختبارات ضغط وخطة استجابة للحوادث |

## 9. إدارة التبعيات وCI/CD

توجد بالفعل ملفات تحقق وبناء في **.github/workflows/validate.yml** و**.github/workflows/build.yml**. قبل إضافة Workflow جديد، حدّد فجوة قابلة للإثبات ولا تكرر الفحوص الحالية.

- احتفظ بأذونات Workflow عند أقل مستوى مناسب، وثبّت إصدارات Actions إلى مراجع موثوقة ومحددة وفق سياسة المشروع.
- افحص أي إضافة خارجية جديدة ومصدرها وترخيصها وسبب الحاجة إليها؛ لا تدمج مكتبة لمجرد أنها شائعة.
- أضف فحصًا آليًا للتبعيات عندما تكون هناك تبعيات قابلة للتعداد وقابلة للفحص بأداة مناسبة. لا تفترض أن أدوات فحص حزم Node أو .NET تنطبق على مشروع GDScript دون ملف تبعيات ملائم.
- فعّل ميزات حماية الأسرار وفحص المستودع من إعدادات GitHub المتاحة للمستودع، ثم تحقق من الإعداد عمليًا؛ وجود ملف Workflow لا يثبت أن إعدادات الحساب مفعلة.
- لا ترفع مفاتيح توقيع الإنتاج إلى CI على فحوص Pull Requests غير موثوقة. افصل بناءات الاختبار عن خطوات إصدار موقّع ذات صلاحيات مقيدة.

## 10. تعريف اكتمال كل تغيير

- [ ] المسؤولية الجديدة واضحة ولا تُنشئ مصدرين متنافسين للحقيقة.
- [ ] قواعد اللعب الجديدة قابلة للاختبار دون بناء المشهد الكامل متى كان ذلك عمليًا.
- [ ] العميل لا يملك قرارًا نهائيًا في حالة اللعب الجماعي الحساسة.
- [ ] الأخطاء والمدخلات غير الصالحة لا تسبب انهيارًا أو فسادًا للحالة.
- [ ] أُضيفت اختبارات ذات صلة أو وُثّق سبب تأجيلها ومخاطر ذلك.
- [ ] عُدّلت الوثائق المتأثرة في Pull Request نفسه.
- [ ] شُغّلت الفحوص المحلية المتاحة، وتُراجع نتائج CI الفعلية قبل الدمج.
- [ ] لم تُضف أسرارًا أو ملفات بناء مولدة أو أصولًا غير موثقة الترخيص.
