## نطاق التغيير

- `scripts/core/save_system.gd`: الإبقاء على `save_game(Dictionary) -> bool` و`load_game() -> Dictionary`، وإضافة `load_game_result() -> Dictionary` لإتاحة حالة الاستعادة دون كسر المستدعين الحاليين.
- `tests/save_system_security_test.gd`: اختبارات الحفظ والنسخة الاحتياطية وحالات التحميل المفقود/التالف.
- `.github/workflows/validate.yml` و`tools/test_ci_security.py`: تشغيل التشخيص محلياً داخل CI وعدم تمرير أسرار خدمة AI إلى Workflow الذي يشغّل شيفرة Pull Request.
- `docs/TEST_PLAN.md`: توثيق طريقة التشغيل وحدود السياسة.

## بروتوكول الحفظ

1. تحويل القاموس إلى JSON ورفض بيانات فارغة أو يتجاوز حجمها 1 MiB.
2. الكتابة إلى `user://savegame.tmp` ثم `flush()`، فحص خطأ الكتابة، إغلاق الملف وإعادة قراءته للتحقق من سلامة JSON وتطابق القاموس.
3. عند وجود حفظ أساسي صالح، نسخ محتواه أولاً إلى `user://savegame.bak.tmp` والتحقق من النسخة المؤقتة؛ ثم تحديث `user://savegame.bak.json` والتحقق منها **قبل تغيير الحفظ الأساسي**.
4. عدم تدوير ملف أساسي تالف إلى النسخة الاحتياطية. هذا يمنع الاستبدال الاعتيادي للنسخة الاحتياطية الصالحة ببيانات تالفـة.
5. نقل الحفظ الأساسي إلى `user://savegame.json.old` قبل ترقية الملف المؤقت. عند فشل الترقية، يحاول التنفيذ إعادة الملف المرحلي إلى المسار الأساسي.
6. يقرأ `load_game_result()` الحفظ الأساسي، ثم الحفظ المرحلي، ثم النسخة الاحتياطية. يعيد حالة واضحة: `ok`، أو `recovered_from_staged_save`، أو `recovered_from_backup`، أو `not_found`، أو `invalid`.
7. يبقى `load_game()` غلاف توافق يعيد القاموس كما اعتاد المستدعون الحاليون. لذلك استخدم `load_game_result()` في واجهة التحميل أو التشخيص إذا كان التفريق بين الفقد والتلف مهماً.

## حدود ضمان سلامة البيانات

هذه الاستراتيجية هي **استعادة مدروسة باستخدام ملف مؤقت ونسخة احتياطية**؛ وليست ادعاءً باستبدال ذري شامل أو بمعاملة تخزين مضمونة عبر جميع أنظمة التشغيل. سلوك إعادة التسمية ودوام البيانات على وحدة التخزين يختلف بحسب المنصة ونظام الملفات، ولا تعادل `flush()` وحدها ضماناً موثقاً لاستمرارية البيانات عند انقطاع الطاقة.

لم يضف هذا التغيير مخططاً دلالياً عاماً لمستويات الصحة والخبرة والجرد والمهام؛ إذ تقبل الواجهة الحالية قاموساً عاماً وتستخدمها أنظمة لعب متعددة. يجب تعريف إصدار المخطط والترحيل بعد جرد كل مستدعي `save_game/load_game` وتحديد الحقول الفعلية، ثم اختبار الملفات القديمة قبل فرض قواعد جديدة.

ولا يغطي الاختبار الحالي انقطاع الطاقة الفعلي أو فشل وسيط التخزين في كل نقطة زمنية. يلزم اختبار تكاملي على Windows وAndroid، بالإضافة إلى فحوص CI على Godot headless، قبل اعتماد جاهزية إصدار إنتاجي.

## أوامر التحقق

من جذر المشروع في بيئة بها Godot CLI المطابق لإصدار المشروع:

```bash
godot --headless --path . --script res://tests/save_system_security_test.gd
godot --headless --path . --script res://tests/gameplay_smoke_test.gd
godot --headless --path . --script res://tests/gameplay_regression_test.gd
```

اختبار الحالة الأساسية ليس بديلاً عن فحص السجل كاملاً. معيار قبول الدفعة هو نجاح هذه الاختبارات في Workflow على **رأس الفرع الحالي**، مع عدم دمجها تلقائياً إلى `main`.
