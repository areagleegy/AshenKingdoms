# خطة التدقيق والإصلاح المرحلي — ممالك الرماد

- **المشروع:** AshenKingdoms
- **تاريخ إعداد الخطة:** 2026-10-20
- **الحالة:** خطة تنفيذ ومراجعة؛ ليست تقريرًا بأن جميع الفحوص نُفذت.
- **الفرع:** `docs/audit-phase-2026-10-20`
- **مصادر الحقيقة:** ملفات المشروع ونتائج CI المرتبطة بالـ commit، لا الملخصات وحدها.

## 1. الغرض والنطاق

تحدد هذه الوثيقة ترتيبًا قابلًا للتدقيق لمراجعة المشروع، وإزالة التناقضات، وتقليل المخاطر، وإكمال الوثائق دون الادعاء بأن الميزات المخططة منفذة. الأولوية هي أن يبقى المشروع قابلًا للفتح والبناء والاختبار، وأن تكون كل خطوة قابلة للمراجعة والتراجع.

النطاق المستهدف للمنتج هو لعبة RPG فانتازيا مظلمة على Android وWeb. اللعب الجماعي ENet تجريبي على المنصات غير Web، وهدف 100 لاعب رؤية بعيدة المدى لا قدرة حالية مثبتة. لا يُعلن دعم اللعب الجماعي في Web قبل اختيار وتنفيذ نقل شبكي مناسب للمتصفح والتحقق منه.

## 2. قواعد التدقيق

1. **لا تغييرات مدمرة مباشرة على `main`:** تُنفّذ الإصلاحات في فرع وتمر عبر Pull Request.
2. **خط أساس قبل التعديل:** سجّل commit البداية، ونتائج CI، والأوامر التي نُفذت، وأي فشل سابق.
3. **إصلاح واحد محدود في كل دفعة:** تجنب إعادة هيكلة واسعة تجمع تغييرات غير مترابطة.
4. **الأدلة قبل الحالة:** لا توصف ميزة أو منصة بأنها مكتملة إلا بدليل قابل لإعادة الإنتاج.
5. **حماية البيانات والأسرار:** لا تُحذف ملفات أو أصول قبل التحقق من عدم استخدامها؛ لا تُضاف مفاتيح توقيع أو أسرار إلى Git.
6. **التوافق:** استخدم Godot 4.6 وإصدارات الأدوات المحددة في ملفات CI؛ لا تغيّر إصدارات الأدوات دون سبب واختبار.
7. **الوثائق مع الكود:** أي تغيير في السلوك أو المسارات أو الاختبارات أو التصدير يجب أن يحدّث الوثيقة ذات الصلة في PR نفسه.
8. **الترخيص:** لا يُقبل أصل خارجي دون مصدر ورخصة وشروط إعادة التوزيع والإسناد، مع مراجعة نص الترخيص الأصلي.

## 4. مراحل التنفيذ وبوابات الانتقال

### المرحلة 0 — تثبيت خط الأساس

- [ ] تحديد commit البداية والفرع الأساسي.
- [ ] مراجعة `.github/workflows/validate.yml` و`.github/workflows/build.yml`.
- [ ] تشغيل `python3 tools/validate_docs.py`.
- [ ] تشغيل `python3 tools/validate_free_assets.py`.
- [ ] تشغيل فحوص Godot المحددة في README وخطة الاختبار.
- [ ] تسجيل كل أمر ونتيجته ورابط CI والـ commit؛ لا تسجل نجاحًا لم يُشاهد.
- [ ] حفظ قائمة الملفات المعدلة قبل أي إصلاح.

**بوابة الانتقال:** يوجد خط أساس يمكن الرجوع إليه، والفشل معروف ومصنف.

### المرحلة 1 — سلامة المشروع والموارد

- [ ] فتح المشروع باستخدام Godot 4.6.
- [ ] تشغيل استيراد الموارد وتحميل السكربتات والمشاهد.
- [ ] مراجعة مراجع `ExtResource` و`SubResource` ومسارات الموارد عند ظهور أخطاء فعلية.
- [ ] التحقق من تسجيل Autoloads في `project.godot` ومطابقتها للمسارات الموجودة.
- [ ] إصلاح أصغر مجموعة أخطاء تكسر التحميل أو التشغيل، ثم إعادة الفحوص.
- [ ] تجنب حذف أي ملف لمجرد أنه يبدو غير مستخدم؛ تحقق من المراجع النصية ومراجع المشاهد وموارد Godot.

**بوابة الانتقال:** المشروع يفتح وتنجح فحوص التحميل المتفق عليها، أو توثّق العوائق المتبقية بدقة.

### المرحلة 2 — اللعب الفردي والحفظ

- [ ] التحقق من الحركة والقتال والصحة والأعداء والجرد والتدرج.
- [ ] اختبار الحوار وقبول المهمة وإتمامها وإعادة تشغيل اللعبة.
- [ ] اختبار الحفظ والتحميل وملف حفظ غير صالح وملف مفقود.
- [ ] التأكد من أن واجهة الهاتف لا تحجب التفاعل وأن التحكم قابل للاستخدام.
- [ ] فصل أي حالة محلية عن حالة الشبكة بوضوح.

**بوابة الانتقال:** سيناريو لعب فردي قابل لإعادة الإنتاج مع نتائج اختبار مسجلة.

### المرحلة 3 — الشبكة والأمن

- [ ] توثيق نموذج السلطة: ما الذي يقرره الخادم وما الذي يرسله العميل.
- [ ] التحقق من ملكية اللاعب لكل طلب ومن حدود الحركة والضرر والنتائج.
- [ ] اختبار انقطاع العميل، والخروج أثناء القتال، والاتصال المكرر، والرسائل غير الصالحة.
- [ ] مراجعة فتح المنافذ وحدود المعدل واستهلاك الموارد.
- [ ] عدم تقديم ENet التجريبي كخدمة عامة آمنة.
- [ ] تحديد قرار مستقل لتوافق Web قبل اختيار التقنية.

**بوابة الانتقال:** اختبارات سلبية موثقة ومراجعة تصميم أمنية؛ لا يعني ذلك اعتماد 100 لاعب.

### المرحلة 4 — حزم المحتوى والأصول

- [ ] اختبار توقيع الفهرس بمفتاح اختبار لا بمفتاح إنتاج.
- [ ] التحقق من رفض توقيع غير صحيح وSHA-256 غير مطابق.
- [ ] رفض مسارات ZIP غير الآمنة والملفات غير المتوقعة والأحجام غير المقبولة.
- [ ] تحديد سلوك الانقطاع والمساحة الحرة والتراجع عن تثبيت فاشل.
- [ ] إبقاء التنزيل الإنتاجي معطلًا حتى نشر خدمة وفهرس ومفتاح عام مضبوطين.
- [ ] مطابقة سجل الأصول مع الملفات الفعلية ونصوص الرخص.

**بوابة الانتقال:** حالات الفشل موثقة والميزة لا تتجاوز إعدادات الأمان الافتراضية.

### المرحلة 5 — Android وWeb والإصدار

- [ ] إنشاء مخرجات CI وتسجيل commit كل مخرج.
- [ ] تثبيت APK على جهاز حقيقي وتسجيل الجهاز والنظام والخطوات والنتيجة.
- [ ] اختبار Web عبر HTTP/HTTPS في المتصفحات المستهدفة، لا من معاينة محلية فقط.
- [ ] قياس حجم البناء والأداء والذاكرة على عتاد محدد.
- [ ] إدارة التوقيع والأسرار خارج المستودع.
- [ ] اتخاذ قرار قبول/قبول مشروط/رفض مع أدلة.

### المرحلة 6 — هدف 100 لاعب

لا تبدأ هذه المرحلة باعتبارها توسعة مباشرة للساحة الحالية. يلزم أولًا تحديد خادم مخصص، ومعدل تحديث الشبكة، ونموذج المحاكاة، والتنبؤ/التعويض عن التأخير، وتقسيم الاهتمام، وحدود الرسائل، والمراقبة، واختبار الحمل والتكلفة. ابدأ بقياس أحجام صغيرة متدرجة، ولا تعتمد سعة 100 لاعب قبل وجود نتائج حمل قابلة للتكرار.

## 6. قواعد الحجم والأداء

- لا تضف مكتبة أو إضافة إلا إذا كانت تحل حاجة مثبتة وتقلل المخاطر أو تكلفة الصيانة.
- فضّل أدوات Godot المدمجة وGDScript في الأنظمة الحالية ما لم تظهر حاجة مقاسة إلى بديل.
- لا تضف أصولًا كبيرة أو مكررة؛ راقب حجم APK/Web وحجم الذاكرة بعد كل دفعة أصول.
- لا تنفذ تحسينًا مبكرًا بناءً على الانطباع؛ سجّل خط أساس ثم قِس.
- لا تختزل الأمن أو الاختبارات لمجرد تقليل الحجم.
- اجعل ميزات الشبكة والتنزيل الاختيارية معطلة افتراضيًا حتى اجتياز بواباتها.
